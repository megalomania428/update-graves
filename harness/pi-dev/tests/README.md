# OAuth fingerprint для compact и tree

## Область действия

Проверенный baseline – установленный `pi-coding-agent` 0.85.1 с его вложенными `pi-ai` и `pi-agent-core` 0.85.1. Верхнеуровневый `pi-agent-core` 1.1.0 не используется: `StreamFn` выводится из публичной сигнатуры `compact`. Наличие модели Opus 5.5 в живом каталоге не предполагается: offline adapter fixture построена из найденной записи Opus 5 с заменённым id.
Существующий entrypoint `../extensions/aoauth-fingerprint-2_1_281.ts` регистрирует `session_before_compact` для manual/threshold/overflow и `session_before_tree` для запрошенного summary непустой ветки. Только model calls Anthropic OAuth проходят изолированную обёртку: предпроверки провайдера и registry auth с повторной проверкой OAuth, затем запрос через `ctx.modelRegistry.runtime.streamSimple`, который перехватывает расширение повторов `review-pi_dev/retry.ts`. Runtime на каждой попытке заново разрешает auth/baseUrl/headers/env. Из полей авторизации обёртка передаёт ему только `apiKey`, `env` и nullable headers вызывающего, без значений preflight auth; остальные опции вызывающего (`maxTokens`, `reasoning`, `cacheRetention`, `sessionId` и прочие) проходят как раньше. Общий fingerprint и тот же factory session header применяются в `transformHeaders` после слияния заголовков runtime, поэтому `x-client-request-id` и дубли в другом регистре не возвращаются в эти заголовки ни на одной попытке; адаптер провайдера, как и до перехода на runtime, сливает их поверх `model.headers`, поэтому ключ, которого нет в заголовках runtime (например, `x-client-request-id` из `model.headers`), уходит в запрос как раньше. Явный `apiKey` вызывающего runtime обрабатывает как API key, без stored OAuth auth и его baseUrl/headers; нативные компакт и tree ключ не передают. Без runtime или его `streamSimple` операция отменяется с категорией `provider` до запроса. Штатные `compact`/`generateBranchSummary` сохраняют summarizer prompts, split history/prefix, instructions, budgets, routing IDs, retry и usage/cost. Ordinary fingerprint и `move-reminders-2_1_281.ts` не изменены по результатам.
Summary не эмитит остальные provider extension hooks, `context` или `before_agent_start`; `move-reminders` не участвует при любом порядке загрузки. Входящие stream callbacks сохраняются; payload callback исполняется перед summary-only structural guard и fingerprint, response callback не дублируется. Runtime получает сигнал, объединённый через `AbortSignal.any` из сигнала события и локального: abort события прекращает ожидание и повторы перехвата, а сбой payload callback или structural guard прерывает локальный сигнал, поэтому такой запрос не повторяется, и операция отменяется с категорией `summary`. Проверка terminal response отвергает `aborted` и успешный stop без непустого текста до добавления штатных файловых XML sections. Для Opus 5/5.5 сохранена прежняя нормализация fingerprint: служебный пустой effort tail и message-level output_config удаляются из final body; это не отдельное исправление effort controls.

## Ошибки и ограничения

No-stream sentinel `No content to summarize` принимается только для фактически metadata-only ветки: подготовка нормализованных entries без лимита должна вернуть ноль сообщений и пустые Sets `read`/`written`/`edited`. Budget-empty с реальным содержимым отменяется с категорией `summary`, без checkpoint/fallback; штатные бюджеты и non-OAuth pipeline не меняются.
Любая ошибка внутри целевого hook возвращает cancel и безопасное уведомление с категорией `auth`, `settings`, `provider`, `summary`, `metadata` или `aborted`, без raw diagnostics/auth/history. Ошибка самого уведомления не разрешает fallback. Ядро представляет неудачу как обычную отмену. Отмена overflow не запускает compaction-triggered retry, но queued messages могут продолжить ход; threshold cancellation также не останавливает весь agent run. Auth failure, произошедший в ядре до hook, расширению недоступен.
Обязателен exclusive-owner режим: расширение должно быть единственным владельцем результата обоих session-before hooks. Runner не является middleware: поздний truthy instruction/label result способен стереть summary и разрешить default path, ранние return-based modifiers не видны; ранний/поздний cancel соблюдается, но поздний не возвращает потраченные токены. Автоматического устранения конфликтов с неизвестными расширениями нет.
Settings читаются одним доверенным snapshot на операцию через `SettingsManager.create` с project trust и `drainErrors`, без setters/flush; чтение может использовать кратковременный lock. Private ephemeral SDK settings и штатные retry UI events публичному context недоступны. Abort прекращает ожидание auth и предотвращает поздний provider dispatch, но физически отменить OAuth refresh публичным registry API невозможно.
Own marker `aoauthFingerprintSummary: 1` признаётся только с двумя полностью валидными массивами строк. Гарантируются compact→compact, branch→branch и own branch→compact в потребляемом диапазоне, включая OAuth→non-OAuth→OAuth. На non-OAuth действует только metadata bridge: aliased read/edited Sets и элементы исходного tree array, без auth/settings/provider/fingerprint. Native результаты не усыновляются marker; original entry objects не меняются. Штатный metadata gap compact→tree намеренно сохранён на обоих типах providers: tree не наследует compaction.details. Чужие fromHook schemas не поддерживаются.
Установка, reload, изменение настроек, ядра self/web и сервисов не выполнялись. Существующей регистрации entrypoint достаточно; новые factory handlers станут доступны после самостоятельного reload пользователем. Текущая активная сессия и историческая ошибка с версией `2.1.151` живым запросом не проверялись.

## Offline запуск

Из корня репозитория, без запуска Pi или сервисов:

```bash
harness/pi-dev/tests/run-tests.sh
```

Скрипт запускает себя в одноразовом podman-контейнере `mirror.gcr.io/library/node:24-trixie-slim`, ставит в нём runtime и выполняет все `run-*.mjs` и `tsc --noEmit` по всем `tsconfig*.json` этого каталога и подкаталогов. Новый тест добавляется своими файлами, скрипт не меняется. Loader использует уже установленный Node 24 и jiti 2.7, отключает `fsCache`/`moduleCache`, проверяет реальное разрешение nested agent-core 0.85.1 из coding-agent, изолирует HOME/agent dir в `/tmp`, очищает окружение и запрещает немокированный fetch. Credentials, реальная история и settings не читаются. Fake settings – `SettingsManager.inMemory`; production factory проверяется через scoped mock `SettingsManager.create`. Настоящий move-reminders загружается из неизменённой временной копии с fake prompt config, без реальных config/инструкций.
Префикс runtime задаётся `AOAUTH_RUNTIME_NODE_MODULES`, по умолчанию `/home/coder/.local/pi-dev/node_modules`. При другом префиксе одновременно требуется согласованная замена абсолютных paths/typeRoots адресного tsconfig, в том числе на nested agent-core, а не root 1.1.0. Генераторы штатные; временный SDK facade только для адресной инъекции некорректных generator results/подсчёта StreamFn. Native preparation для chain-тестов читается из installed dist, production использует только публичные root exports. Временные файлы удаляются, в репозитории cache/logs не создаются.
Frozen fixture `fixtures/ordinary-281.json` снята с исходного entrypoint до рефакторинга: known hash `b83`, headers, billing, betas и Opus transformations. Session UUID нормализован, OS/arch зависят от платформы. Один test-файл проверяет ordinary regression, factory integration, реальные fake-fetch adapter bodies, retries/callback counts, перехват повторов runtime, abort/auth, metadata bridges, sentinel/error semantics и ограничения runner. Live LLM requests, полные suites и сборки не выполняются. Runtime реестра в тесте выполняет настоящие `streamSimple` и подготовку запроса `ModelRuntime` над фейковыми provider и auth, а перехват повторов `retry.ts` эмулируется в самом тесте: `retry.ts` лежит вне этого репозитория и в контейнер `run-tests.sh` не монтируется.

Тесты импортируют fingerprint и summary helpers из одного entrypoint `../extensions/aoauth-fingerprint-2_1_281.ts`. Отдельного модуля для summary нет.

## Claude Code 2.1.322

Версионный runner `run-aoauth-fingerprint-2_1_322.mjs`, тест и tsconfig теперь действительно загружают расширения 322, а не копии 281. `fixtures/interactive-322.json` содержит независимо снятые интерактивные значения Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.1 и Fable 5.2: identity headers, порядок betas, billing, thinking, context management и штатные бюджеты. Исходный `~/.local/share/claude/versions/2.1.322` запускался через PTY без `-p`, с fake OAuth и mini-server внутри `unshare -Urn`; внешних интерфейсов в namespace нет, loopback поднимается отдельно. Реальные credentials и пользовательские настройки не копируются.

Fingerprint 322 использует Stainless `0.128.0`, runtime `v26.12.1` и billing `2.1.322`; для указанного тестового запроса `Reply with one word: hello` hash равен `91f`. Новые модельные beta-наборы взяты из перехватов, включая особый порядок Haiku. Для этих пяти моделей adaptive thinking получает `display: 'updates'` без `block_binding`; из распознанного текущего effort tail копируется только `effort` в верхнеуровневый `output_config`, а в обычном запросе начальный effort объединяется с native system reminder. Дополнительные per-message controls, неизвестные поля сообщения и некорректные tails сохраняются в исходной области, без переноса `format` и других настроек на весь запрос. Исторические per-message controls и непустые system reminders сохраняются – в 322 это валидный формат, в отличие от старой нормализации 281. При assistant history, более ранних per-message controls, automatic cache или непустой caller system section текущий пустой system control также сохраняется, даже без assistant: иначе предыдущий per-turn effort перекрыл бы новый верхнеуровневый. Это отдельно сверено с интерактивным native переходом `medium → high`; summary-only запрос без assistant messages по-прежнему не получает лишнего пустого tail. Штатный `clear_thinking_20251015` с `keep: 'all'` добавляется только при отсутствии caller context management. Неизвестные модели сохраняют собственные betas и controls, а legacy Opus 5 – прежнюю нормализацию неподдерживаемых полей. Заголовок `user-agent` записывается в нижнем регистре: иначе штатный адаптер мог перезаписать результат хука своим `claude-cli/2.1.251`. Проверка настоящего адаптера сравнивает фактические HTTP-заголовки всех пяти моделей, а не только объект до сериализации.

Отдельные move-тесты используют настоящую конфигурацию и hashes исходных перехватов без добавленного завершающего перевода строки. Проверяются native порядок user/system, cache markers, worktree notice, сохранение изображений и истории, текущего и исторического effort, Happier и CLI append prompts, отсутствие фиксированного billing hash и оба порядка хуков. Поле billing принадлежит только fingerprint; move сохраняет уже вычисленный блок. У новых system-шаблонов завершающий перевод строки файла не попадает в блок запроса; у attribution reminder он сохраняется, как в исходном запросе.

Дополнительная интеграционная проверка загружает настоящий `compact-context.ts` вместе с fingerprint и move-reminders в обоих порядках для каждой из пяти моделей. Успех создаёт ровно один checkpoint и продолжение с usage и `next`; сбой OAuth summary отменяет операцию без нативного fallback и возвращает продолжение с безопасной ошибкой. Существующие проверки manual/threshold/overflow, split turns, tree, retry, abort и metadata chains сохранены. Локальные интерактивные прогоны Pi дополнительно проверяют полный цикл tool call → summary → продолжение и отказ mini-server с HTTP 400; эти прогоны не отправляют запросы настоящим LLM.

Явно запрошенные caller beta-флаги сохраняются с дедупликацией в header и payload, включая новые features, неизвестные расширению. Исключение – известные взаимоисключающие версии server-side fallback: array `fallbacks` требует точно `server-side-fallback-2026-06-01`, а scalar `'default'` – `server-side-fallback-2026-07-01`; несовместимый SDK/caller fallback-флаг заменяется соответствующим фактической форме body. Дополнительные обязательные флаги известных включённых SDK features добавляются к захваченному native beta-набору: server-side fallback сохраняет поле `fallbacks` и его отдельный array/default протокол, а отключённый eager input streaming сохраняет `fine-grained-tool-streaming-2025-05-14` при наличии tools. Для `clear_at: 'next_user_message'` сохраняется `mid-conversation-system-clear-at-2026-08-21`; scoped text не считается допустимой целью автоматического кеширования. Реальный адаптер проверяется для всех пяти моделей, обычного запроса и изолированного summary, с обеими features по отдельности, вместе и без них. Старые beta-наборы Sonnet 5, Opus 5/4.8/4.7 и их reminder variants проверяются по независимому `legacy-322.json`, извлечённому из указанного в нём базового коммита; это проверка сохранения конфигурации и прежнего поведения, не новые native captures этих моделей и не утверждение о побайтовом равенстве всех dereferenced legacy prompts. Общий Git footer обновлён по native capture с прежним смыслом начального snapshot.

При replay `thinking`/`redacted_thinking` с adaptive thinking сохраняется явная политика `block_binding`, а при её отсутствии используется `prefix_mismatch_behavior: 'drop_block'` с обязательным `thinking-binding-controls-2026-08-01`. Это защищает client-side compact с retained thinking от потери SDK prefix-check control: неизменённые opaque blocks передаются без редактирования, но несовместимый с новым prefix блок может быть отброшен сервером вместо 400. Явный режим `error` не подменяется. Первичный запрос без replay и изолированный summary сохраняют захваченную native форму без этого автоматически добавленного control. Реальный адаптер проверяется для пяти моделей, обычных и redacted blocks и трёх вариантов политики; криптографическая валидность тестовых подписей и реальная серверная проверка офлайн не подтверждаются.

В native-пути нормализуются только распознанные default SDK cache markers последнего immediate tool (перед deferred tools) и последнего text/tool_result-блока; явно заданные TTL и image markers сохраняются. Нативные markers добавляются в пределах доступного бюджета и порядка TTL, только при включённом SDK cache; на followup environment не получает новый breakpoint. Идентичный default-маркер, вручную заданный в той же позиции, неотличим от SDK-generated. Обычный fingerprint не удаляет начальный SDK effort control: иначе следующий запрос вставил бы отсутствовавший historical control перед signed thinking. Только изолированный summary runtime явно включает summary-only нормализацию чистого initial tail. Environment получает effort лишь из наблюдаемого per-message control, не из top-level effort при unmanaged модели. Default `context_management` не добавляется, когда caller уже задал `compaction`, поскольку on-demand server compaction несовместим с этим полем.

В default-пути environment вставляется после всей первой группы user-сообщений. При любом automatic cache или существующей caller system section environment всегда находится в постоянном top-level system block, независимо от текущего бюджета: перенос cache marker на следующий user turn не меняет ранний prefix. Caller system messages и effort controls остаются отдельно и без переписывания. Consecutive nonempty system messages рассматриваются как одна section, с прежними ограничениями для её соседей user/server tool и assistant/конец, а не ошибочно отвергаются по отдельности. Совпадающие automatic и explicit breakpoint с одинаковым TTL занимают один слот. Nullable `cache_control: null` означает отсутствие marker и не включает автоматическое или SDK кеширование; счётчик учитывает cache marker внутри `tool_addition.tool.definition` только для документированной формы `tool_definition`, не внутри произвольного `input_schema` или JSON пользователя. При unmanaged adaptive SDK без наблюдаемого per-message effort initial/followup environment не получает придуманного `output_config` и сохраняет форму content при replay. Tool results остаются перед обычным текстом, historical effort не выдумывается из текущего. Подстановки global/local instructions выполняются буквально и за один проход, включая `$`-последовательности и вложенные `{{crs_…}}` в самих инструкциях.

Mini-server дополнительно проверяет полный сериализованный body, включая tool definitions: не больше четырёх cache breakpoints, длинный TTL перед коротким, допустимых соседей непустого system-сообщения и порядок/matching `tool_result`. Конфигурационные system turns без текста проверяются отдельно от текстовых reminders. Эти проверки применяются к обычному запросу, tool loop, summary и продолжению после компакта; одного успешного SSE-ответа для приёмки недостаточно. Это локальная проверка указанных инвариантов, а не обращение к настоящему API и не полная реализация его JSON Schema. Исключение обычного `before_provider_request` перехватывается публичным runner Pi с сохранением предыдущего payload; этот hook не является блокирующим API firewall. Fail-closed ниже относится к отдельному OAuth summary runtime, а не к произвольному невалидному caller payload.

Тексты о Claude Code tools, agents и skills в model reminders намеренно сохраняются из оригинального перехвата: это часть запрошенного native prompt parity и прежней архитектуры расширения. Они не регистрируют `Agent`, `ToolSearch`, `Skill` или новые навыки в Pi; фактические доступные инструменты задаются собственными tool definitions Pi. Динамическая замена этих текстов нарушила бы поблочное соответствие исходным промптам. Приёмочные settings явно загружают 322 extensions; шаблон `harness/pi-dev/agent/settings.json` по-прежнему выбирает 281 и не переключается автоматически этой доработкой.

Сравнение Claude и Pi относится к fingerprint, системным текстам, model reminders и соответствующим controls при одинаковом effort и бюджете. Собственные схемы инструментов Pi, native safeguards Claude Code, transport headers fetch/Bun, длина тела и случайные session/metadata IDs не подменяются: это разные harness, а не побайтовые копии всего HTTP-запроса. Настройки effort, бюджеты и инструкции суммаризации Pi не заменяются значениями обычного Claude Code запроса.

## compact-context

Entrypoint `../extensions/compact-context.ts` регистрирует инструмент `compact_context` с опциональными `instructions`, `next` и `minContextTokens` (целое не меньше 1). Описание для модели запрещает вызывать его по своей инициативе: только по явному указанию пользователя или skill и только единственным вызовом инструмента в сообщении, а в `next` предлагает записать, что сделать сразу после компакта, например заново прочитать файл skill и журнал прогона. Там же сказано, что с `minContextTokens` вызов при меньшем или неизвестном размере контекста пропускается и сразу возвращается, ход продолжается, и дальше нужно выполнить следующее запланированное действие, например `yield_to_subsessions`.
`execute` не вызывает `ctx.compact()`: `AgentSession.compact()` начинается с `abort()` и прервал бы соседние вызовы инструментов той же пачки. Инструмент запоминает запрос, переходит из `idle` в `requested` и возвращает результат с `terminate: true`: `success: true`, `tokens`, `minContextTokens`, `contextWindow`, `percent` и `message` об отложенном старте, а при уже идущем запросе или сообщениях в очереди (`ctx.hasPendingMessages()`) отклоняется ошибкой. Обработчик `tool_call` блокирует `compact_context`, если в сообщении ассистента с этим `toolCallId` есть другие вызовы или такое сообщение не найдено: `terminate` срабатывает, только когда его вернули все результаты пачки.
Порог `minContextTokens` проверяется в `execute` после отказа при уже идущем запросе и до проверки очереди, поэтому пропуск при сообщениях в очереди возвращает пропуск, а не ошибку. `ctx.getContextUsage()` вызывается один раз в каждом `execute` после этого отказа, порог сравнивается с его `tokens`, а снимок `tokens`, `contextWindow` и `percent` сохраняется в запросе. Если `getContextUsage()` вернул `undefined`, `tokens` равно `null` (например, сразу после компакта до ответа модели) или меньше порога, вызов пропускается: запрос не создаётся, состояние остаётся `idle`, результат возвращается без `terminate`, и ход продолжается. `content` содержит JSON того же объекта, что и `details`: `success: true`, `skipped: true`, `reason` (`unknown` или `below-threshold`), `tokens`, `minContextTokens`, `contextWindow`, `percent` и `message` с причиной пропуска и указанием продолжать задачу по плану. Те же четыре поля есть и в результате запуска: неизвестные значения, в том числе `minContextTokens` без параметра, равны `null`, а `percent` округляется до двух знаков после запятой. При контексте не меньше порога вызов работает как без параметра, а блокировка в `tool_call` действует и на вызовы, которые были бы пропущены.
Компакт стартует в `agent_settled`: состояние `compacting` и `ctx.compact({ customInstructions })` с `ctx` этого обработчика. Если ход продолжился из-за очереди, `turn_start` сбрасывает запрос и отправляет `steer`-уведомление: о повторном вызове или, если Pi уже сжал контекст по порогу, о том, что повторять не нужно, с `next` в конце. Пока именно это уведомление не доставлено (`message_start` сообщения `compact-context` с его номером в `details.notice` или `agent_settled`), `execute` отклоняется: `ctx.hasPendingMessages()` его не видит, и повторный вызов отменялся бы им же по кругу. Esc/Stop до `agent_settled` (прерванный сигнал хода или `session_compact_failed` с `aborted: true` в состоянии `requested` при прерванном сигнале последнего автокомпакта, запомненном из `session_before_compact` с `threshold` или `overflow`) отменяет запрос с уведомлением в UI; отмена автокомпакта расширением или неизвестный сигнал запрос не отменяют, и в `agent_settled` стартует свой компакт, а занятая сессия (`!ctx.isIdle()` или очередь) даёт сообщение о том, что компакт не запущен: при идущем ходе (`ctx.signal` задан) – `followUp`, без хода – `nextTurn` и уведомление в UI, чтобы не запустить ход параллельно чужому компакту. Если после запроса Pi сам сжал контекст (`session_compact` с `threshold` или `overflow`), `ctx.compact()` не вызывается и сразу уходит продолжение об успехе.
Продолжение отправляется через `pi.sendMessage` с `customType` `compact-context`, `triggerTurn: true` и `deliverAs: 'followUp'`, `next` дописывается в конец. После успешного `ctx.compact()` и после автокомпакта Pi (продолжение из `agent_settled` и уведомление из `turn_start`) перед блоком `next` добавляются строка `Context usage:` и блок `json` с JSON с отступом 2: `tokensAtCall` и `percentAtCall` из снимка вызова, `tokensBefore`, `percentBefore`, `tokensAfter`, `percentAfter`, `contextWindow` и `minContextTokens`; те же поля дописываются в `details`. `tokensBefore` берётся из `CompactionResult` или из `compactionEntry` автоматического `session_compact`, `tokensAfter` – из `estimatedTokensAfter`, а без него и при автокомпакте – оценкой Pi `estimateTokens` по `buildSessionContext` ветки до последней записи `compaction`. `contextWindow` берётся из `ctx.getContextUsage()` в момент продолжения, иначе из снимка вызова, проценты округляются до двух знаков, неизвестные значения равны `null`. При `Already compacted` и ошибках блока нет. Ошибка сжатия даёт продолжение с текстом ошибки, `Already compacted` считается успехом, если после запроса пришло `session_compact`, а отмена (`Compaction cancelled` или `AbortError`) решается по сигналу компакта. Обработчик `session_before_compact` ничего не возвращает и в состоянии `compacting` запоминает сигнал первого события с `reason: 'manual'`. Прерванный сигнал (Esc/Stop, `abort()`) даёт только уведомление при наличии UI, а непрерванный или неизвестный, если обработчик не вызывался, означает отмену хуком другого расширения, например после сбоя OAuth-сводки, и даёт продолжение с ошибкой `Compaction was cancelled by an extension, for example after an OAuth summary failure.` Обработчик видит событие, только если compact-context загружен раньше расширения, которое возвращает `cancel`: `ExtensionRunner.emit` прекращает обход на первом `cancel`. `session_shutdown` сбрасывает состояние в `idle`, и поздние callbacks прежней операции игнорируются.
Тест `compact-context.test.ts` использует strict fake pi/ctx, loader `run-compact-context.mjs` и `tsconfig.compact-context.json` подхватываются `run-tests.sh` без изменений. Loader берёт runtime из `COMPACT_CONTEXT_RUNTIME_NODE_MODULES`, по умолчанию `/home/coder/.local/pi-dev/node_modules`, и через alias jiti разрешает `typebox` из вложенных зависимостей `pi-coding-agent` 0.85.1, а сам `@earendil-works/pi-coding-agent` – в его `dist/index.js`, потому что entrypoint импортирует из него функции, как и Pi при загрузке расширений.
