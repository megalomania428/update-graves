# Этап 4. Финальное ревью

<!-- markdownlint-disable-file MD013 -->

- Сначала финальное ревью проводит вся компашка `reviewer`: подготовить задания и провести раунд по `review-cycle.md`. Передать пути к файлам:
  - `task.md` – моё исходное задание;
  - `decisions.md` – вопросы и мои ответы;
  - одобренную спеку с решениями по вопросам, её каталоги вложений и правок и diff полных замен;
  - спеки исправлений, если были;
  - сводный `facts-<N>.md`;
  - `autonomous-decisions.md` и `criteria.md`, если есть;
  - `deferred.md`, если есть, – исправления спеки без повторного ревью: каждое проверить на коде;
  - diff от `T0` до текущего снимка, собранный `scripts/review-bundle.sh`.
- При первом финальном ревью требовать от каждого ревьюера до открытия спек и diff выписать по `task.md` и `decisions.md` нумерованный список требований и крайних случаев в `plan-reviewer-4-<N>-<модель>.md`.
- Задача роли `reviewer` – проверить результат по `task.md`, `decisions.md` и `autonomous-decisions.md`, а не по спеке: каждое требование свести к строке diff или к замечанию «не реализовано», искать сценарии поломки и изменения вне scope. Соответствие спеке вторично. Первый полный раунд проверяет весь контракт, каждое автономное решение, все принятые свойства и области из `criteria.md` и каждый пункт `deferred.md` на коде, а не только отдельные места.
- Ошибки финального ревью, скорее всего, сложные и неочевидные: по принятым замечаниям написать `fix-spec-<N>.md` по правилам спеки исправлений из `stage-3.md` с обязательным тестовым покрытием ошибок кода продукта по `references/tests.md` и выполнить её ролью `executor` по `stage-3.md`, включая цикл доработки. Принятые замечания компашки и экспертов исправляются только так; независимые замечания одного раунда – одной спекой исправлений. `INFO` применяется по усмотрению оркестратора, но если применяется – в той же спеке исправлений.
- Изменение для повторного ревью и перепроверки автором – diff от снимка прошлого ревью до текущего. Вместе с ним передаётся полный актуальный материал из списка выше; одним diff его не заменять. При возврате на этап 3 исходный `T0` сохраняется.
- Проверка исправлений компашки – по тяжести:
  - `CRIT` и механизм, переписанный заново, – полный раунд компашки;
  - `WARN` – перепроверка автором по `review-cycle.md`;
  - `INFO` – оркестратор сам читает diff исправления.
- Когда цикл компашки пройден по `review-cycle.md`, подготовить задания паре `expert`, выполнить условный компакт и запустить пару: она один раз проверяет весь diff от `T0` с теми же файлами и задачей, что у компашки. До открытия спек и diff каждая модель пишет список требований и крайних случаев в `plan-expert-4-<N>-<модель>.md`. Формат замечаний и шкала тяжести – из `review-cycle.md`.
- Замечания экспертов разбирать так:
  - принятые исправлять по общему правилу: `fix-spec-<N>.md` → `executor` → проверка по этапу 3;
  - по отклонённым оркестратором сразу проводить консультацию по `review-cycle.md` со всеми работающими ревьюерами компашки, недоступных по лимитам не ждать, повторный полный проход эксперта не запускать. Исключение: понижение или отклонение `CRIT` обязательно передать автору с причиной и дождаться ответа по `review-cycle.md`; до ответа замечание открыто. При недоступности автора ответ по замечанию даёт назначенный работающий `reviewer`, замена записывается в журнал; вопрос по `autonomy.md` требуется только при недоступности роли или отсутствии кворума, не из-за лимитов одной модели. До ответа назначенной модели замечание остаётся открытым. После консультации и ответа по `CRIT` при отклонении замечание закрывается, иначе исправляется по общему правилу;
  - `INFO` после исправления проверяет оркестратор по diff исправления;
  - `WARN` после исправления перепроверяет одна работающая модель компашки по правилам перепроверки автором из `review-cycle.md`, с файлом замечаний эксперта вместо своего; модель для каждого замечания выбирает оркестратор и записывает в журнал. Её новые замечания разбираются по тем же правилам, новый `CRIT` – полным раундом компашки;
  - `CRIT` после исправления один раз перепроверяет только нашедшая его модель-эксперт по правилам перепроверки автором. Если `CRIT` нашли обе модели, достаточно одной из нашедших по выбору оркестратора; выбор записывается в журнал. Если нашедшая модель недоступна, его проверяет полный раунд компашки;
  - если после перепроверки `CRIT` остался `NOT ADDRESSED`, дальше его проверяет полный раунд компашки. Повторно экспертов для перепроверки не вызывать;
  - механизм, переписанный заново, – полный раунд компашки.
- Поводы спрашивать меня по ревью – только из `references/autonomy.md`.
- Цикл продолжается, пока цикл компашки не пройден по `review-cycle.md`, замечания экспертов не закрыты, а оркестратор не считает итог соответствующим `task.md`, `decisions.md` и `autonomous-decisions.md`.
- После одобрения итога сделать в `WT_DIR` один коммит всех изменений командой `scripts/commit-project.sh "${WT_DIR}" "${MESSAGE}" [<путь>…]`:
  - проверить `git -C "${WT_DIR}" status --short`: если там только файлы из одобренного diff от `T0` – запускать без путей, иначе перечислить только эти файлы поимённо, без установленных зависимостей и посторонних файлов;
  - сообщение в переменной `MESSAGE` – одна строка в стиле последних коммитов проекта из `git -C "${WT_DIR}" log --format=%s -15`;
  - автор, коммитер и запрет трейлеров – по `references/scripts.md`.
- Слияние ветки и удаление worktree выполняю я. В итоговом ответе мне указать `WT_DIR`, ветку, SHA коммита и раздел «Решено без тебя» по `references/autonomy.md`.
