# Задания ролям

Действует на всех этапах.

- Все роли запускать через `spawn_subsession`, передавая модель роли в параметре `model`. Перед каждым запуском отдельной подсессии или параллельной пачки выполнять условный компакт по `references/context.md`; это относится также к повтору после `BLOCKED`, замене модели из-за лимитов и консультации.
- Работа идёт на лэптопе: в каждой спеке для любой роли запрещать длительные тяжёлые тесты, если я явно не разрешил их; разрешение действует только на названные мной команды и объём и передаётся в задании дословно.
- В каждой спеке для любой роли явно запрещать инструменты `spawn_*`, чтобы роль работала в одиночку.
- С файлами проекта все роли работают только в worktree `WT_DIR` из этапа 1, а свои файлы пишут по путям из задания в каталог прогона. Дополнительные рабочие каталоги и worktree допускаются только для операций, прямо предусмотренных инструкциями проекта (`AGENTS.md`, `CLAUDE.md` и подобными), и для удаляемого временного Git-клона технического `scout` по `references/stage-2.md`; подготовку и очистку каталогов по инструкциям проекта обеспечивает оркестратор, а свой временный клон `scout` создаёт и удаляет самостоятельно. PI WEB запускает подсессии в каталоге оркестратора, поэтому в каждом задании для любой роли указывать:
  - абсолютный `WT_DIR` и разрешённые дополнительные рабочие каталоги, если они нужны;
  - команды проекта выполнять через `cd "${WT_DIR}" &&` или `git -C "${WT_DIR}"`; для операций в других разрешённых каталогах явно задавать соответствующий абсолютный рабочий каталог;
  - пути к файлам писать абсолютными; файлы проекта изменять внутри `WT_DIR`, операции в дополнительных каталогах выполнять только в пределах, разрешённых инструкциями проекта и ролью;
  - основную рабочую копию проекта и общие рабочие копии внешних репозиториев не трогать;
  - для всех ролей и всех команд инструментов, включая вспомогательные list/version и установки, явно передавать в каждом задании: `HOME`, `XDG_CACHE_HOME`, `XDG_CONFIG_HOME`, `npm_config_cache`, `GOPATH`, `GOMODCACHE`, `GOCACHE`, `PIP_CACHE_DIR`, `PYTHONPYCACHEPREFIX` и аналогичные используемые кэши, логи и конфиги направлять в собственный удаляемый временный каталог; реальные домашние файлы, кэши и конфиги не менять. Технический `scout` размещает этот каталог строго внутри своего удаляемого клона;
  - зависимости (`node_modules`, venv и подобное) по умолчанию устанавливать вне `WT_DIR` в разрешённую временную область. Внутри `WT_DIR` установка допустима только при подтверждении целевого пути командой `git -C "${WT_DIR}" check-ignore -q -- <путь>` и отсутствии попавших в scope зависимостей в итоговом status. Каталоги установки и сборки, прямо заданные инструкциями проекта, разрешены только по этим инструкциям; это не расширяет запись в общий checkout;
  - выполняющая или проверяющая роль удаляет только собственные временные артефакты; очистка обязательна при успехе и ошибке, чужие файлы не удалять. До снимка и пакета проверить status: зависимости и мусор, не исключённые правилами Git, не должны попадать в снимки и diff. При их наличии остановить зависимую сборку пакета и вернуть выполняющей роли для очистки своих артефактов, не обходить snapshot-скрипт и не исключать произвольно пути из снимка.
- В каждой спеке для ролей `executor` и `fixer` указывать: веток и worktree самостоятельно не создавать, использовать только подготовленные оркестратором рабочие каталоги; в проекте и дополнительных worktree ничего не коммитить.
- Репозитории GitHub все роли, включая оркестратора, изучают локально: сначала искать `/workspace/github/<репо>`, затем другие клоны под `/workspace/github` по remote URL. Общий checkout не менять; обновлять только `fetch`, SSH remote предварительно переводить на HTTPS, если это разрешено инструкциями проекта. До нового клонирования проверить успешность запроса API и размер в КБ через `curl -sf https://api.github.com/repos/<владелец>/<репо>` и разбор поля `size` посредством `jq`. Новый `git -C /workspace/github clone https://github.com/<владелец>/<репо>` разрешён только при успешном запросе и подтверждённом числовом размере от `0` до `1048576` КБ включительно. При большем размере изучать удалённо. При ошибке API/HTTP или разбора, `null`, пустом либо нечисловом ответе размер неизвестен: не клонировать и не считать его нулём; изучать удалённо либо задать обязательный вопрос, если без локального дерева задачу выполнить нельзя. Для патчей соблюдать инструкции проекта о дополнительных рабочих каталогах. В каждом задании явно передавать это правило; техническому `scout` запрещена запись в общие клоны и их конфигурацию.
- Артефакты передавать ролям путями к файлам в каталоге прогона, а не вставлять их содержимое в текст задания. Для первоначальной спеки передавать существующие вложения, файлы правок и diff замен с манифестами текста спеки. Техническая и выполняющая роли явно сверяют SHA256 самого существующего diff замен по этому манифесту как часть одобренного комплекта до применения; несовпадение – `BLOCKED`, без применения. Без полных замен diff и его манифест не требуются. При частичных правках сохранять исходные окончания строк по `stage-2.md`; невозможность однозначной точной замены – `BLOCKED`, без нормализации. Для `fix-spec` они не передаются и не применяются повторно. Обычный `scout` ничего в проекте не меняет; технический `scout` проверяет каждую версию по этапу 2 только в своём временном клоне, подставляя его путь вместо `WT_DIR` во все команды. Его внутренний отчёт и симуляция не передаются `reviewer` и `expert`.
- Задания ролям `reviewer` и `expert`, разбор их вердиктов, `BLOCKED`, `DISPUTED` и консультации – по `references/review-cycle.md`.
- Роли `executor` и `fixer` пишут полный отчёт в файл, путь к которому указан в задании: что сделано, какие проверки запускались с командами и результатами, отклонения от спеки, сомнения. В ответе возвращают только статус и одну строку сути:
  - `DONE` – сделано;
  - `DONE_WITH_CONCERNS` – сделано, но есть сомнения: прочитать их в отчёте до проверки;
  - `NEEDS_CONTEXT` – не хватает информации: дополнить задание и запустить роль заново;
  - `BLOCKED` – выполнить невозможно: если проблема в спеке этапа 2, вернуться к этапу 1 или 2, если в спеке исправлений – исправить её саму и запустить роль заново.
