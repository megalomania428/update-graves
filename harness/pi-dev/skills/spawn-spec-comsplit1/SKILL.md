# Доработка через цепочку агентов

Задача передаётся аргументом команды и приходит в конце скилла как `User: …`.

## Содержание

`SKILL_DIR` – каталог файла из атрибута `location` блока `<skill …>`; пути `references/…` и `scripts/…` ниже относительны ему. В этом файле – правила для всех этапов, а порядок действий каждого этапа лежит в отдельном файле `references/`. Такой файл читать целиком инструментом чтения при наступлении условия и не раньше, чтение записывать в журнал; действия этапа без прочитанного файла этапа не выполнять:

- вход в этап 1 → `references/stage-1.md`;
- вход в этап 2 → `references/stage-2.md` и `references/review-cycle.md`;
- вход в этап 3, в том числе выполнение спеки исправлений после финального ревью → `references/stage-3.md`;
- вход в этап 4 → `references/stage-4.md` и `references/review-cycle.md`;
- скрипты из `scripts/` запускать, а не перечитывать; их назначение и аргументы – в разделе «Скрипты».

После сжатия контекста перечитать этот файл, файл текущего этапа и `references/review-cycle.md`, если текущий этап – 2 или 4.

## Роли

Модели задаются только в этом разделе, остальной текст ссылается на роли.

- `скаут` – основная `anthropic/claude-sonnet-5-5:medium` и вторая `openai-codex/gpt-6.1-sol:medium`: поиск фактов для вопросов. При ошибке лимитов одной работает другая. Ничего не изменяет, кроме своих файлов в каталоге прогона.
- `ревьюер` – компашка `openai-codex/gpt-6-luna:max`, `openai-codex/gpt-6.1-terra:medium`, `anthropic/claude-haiku-5-5:max` и `zai/glm-5.3-flash:max`: ревью спеки и финальное ревью, все одновременно. Если у кого-то ошибка лимитов, продолжать с оставшимися и записать это в журнал.
- `эксперт` – пара `anthropic/claude-fable-5-1:high` и `openai-codex/gpt-6-astra:high`: финальная проверка кода, только после одобрения компашкой `ревьюер`, обе одновременно. Если у одной ошибка лимитов, работает другая.
- `исполнитель` – `anthropic/claude-sonnet-5-5:max`: первичное выполнение спеки и исправление ошибок финального ревью, `openai-codex/gpt-6.1-sol:max`, если от первого прилетела ошибка лимитов.
- `доработчик` – для простых исправлений `anthropic/claude-haiku-5-5:max`, при ошибке лимитов `openai-codex/gpt-6-luna:max`; для сложных исправлений `anthropic/claude-sonnet-5-5:max`, при ошибке лимитов `openai-codex/gpt-6.1-sol:max`: исправление недоделок по итогам промежуточной проверки. Вариант выбирает оркестратор перед каждым запуском по правилам этапа 3; при недоступности обеих моделей выбранного варианта действует общее правило недоступности роли.
- `оркестратор` – текущая сессия: вопросы, сведение отчётов скаутов в своём контексте, спеки, проверки, запуск остальных ролей, коммиты в репозиторий спек, создание worktree проекта и один итоговый коммит в нём. Код проекта самостоятельно не правит. Автор и коммитер коммитов – `Moderator <moderator@models.dev>`: значения зашиты в `scripts/commit-specs.sh` и `scripts/commit-project.sh`.

## Общие правила

- Все роли запускать через `spawn_subsession`, передавая модель роли в параметре `model`. Перед каждым запуском отдельной подсессии или параллельной пачки выполнять условный компакт по разделу «Управление контекстом»; это относится также к повтору после `BLOCKED`, замене модели из-за лимитов и голосованию.
- Все вопросы пользователю, включая уточнения, согласования, продолжение после 33 раундов и остановки по ошибкам, задавать только через `ask_user`. Текстовое сообщение с вопросом вместо вызова инструмента запрещено. Готовые независимые вопросы объединять в один вызов; вызывать `ask_user` единственным инструментом в сообщении и последним действием хода, затем ждать ответа. Не повторять отправленные вопросы; оставленные без ответа считать открытыми, не подставлять рекомендуемый вариант молча.
- Если недоступны все модели роли, остановиться и спросить меня.
- Работа идёт на лэптопе: в каждой спеке для любой роли запрещать длительные тяжёлые тесты.
- В каждой спеке для любой роли явно запрещать инструменты `spawn_*`, чтобы роль работала в одиночку.
- С файлами проекта все роли работают только в worktree `WT_DIR` из этапа 1, а свои файлы пишут по путям из задания в каталог прогона. Дополнительные рабочие каталоги и worktree допускаются только для операций, прямо предусмотренных инструкциями проекта (`AGENTS.md`, `CLAUDE.md` и подобными); их подготовку и очистку обеспечивает оркестратор по этим инструкциям. PI WEB запускает подсессии в каталоге оркестратора, поэтому в каждом задании для любой роли указывать:
  - абсолютный `WT_DIR` и разрешённые дополнительные рабочие каталоги, если они нужны;
  - команды проекта выполнять через `cd "${WT_DIR}" &&` или `git -C "${WT_DIR}"`; для операций в других разрешённых каталогах явно задавать соответствующий абсолютный рабочий каталог;
  - пути к файлам писать абсолютными; файлы проекта изменять внутри `WT_DIR`, операции в дополнительных каталогах выполнять только в пределах, разрешённых инструкциями проекта и ролью;
  - основную рабочую копию проекта и общие рабочие копии внешних репозиториев не трогать;
  - установка зависимостей (`node_modules`, venv и подобное) разрешена внутри `WT_DIR` либо в дополнительных каталогах, прямо назначенных для этого инструкциями проекта.
- В каждой спеке для ролей `исполнитель` и `доработчик` указывать: веток и worktree самостоятельно не создавать, использовать только подготовленные оркестратором рабочие каталоги; в проекте и дополнительных worktree ничего не коммитить.
- Репозитории GitHub все роли, включая `оркестратор`, изучают только локально: сначала искать клон в `/workspace/github/<репо>`, а если его нет – выполнить `git -C /workspace/github clone https://github.com/<владелец>/<репо>`. Исключение – репозитории больше гигабайта: перед клонированием сверить размер в КБ через `curl -s https://api.github.com/repos/<владелец>/<репо> | jq .size`, и при значении больше `1048576` не клонировать, а изучать удалённо. В каждой спеке для любой роли указывать это правило явно.
- Артефакты передавать ролям путями к файлам в каталоге прогона, а не вставлять их содержимое в текст задания.
- Каждый цикл с ролями – ревью спеки, доработка, финальное ревью – не больше 33 раундов подряд, лимит считается для каждого цикла отдельно. После 33 раунда с незакрытыми замечаниями сохранить их, выполнить условный компакт по разделу «Управление контекстом», затем через `ask_user` показать оставшиеся замечания и спросить, продолжать или нет. Это ограничение числа раундов, а не периодичность компакта; без разрешения следующий раунд не запускать.
- Задания ролям `ревьюер` и `эксперт`, разбор их вердиктов, `BLOCKED`, `DISPUTED` и голосования – по `references/review-cycle.md`.
- Роли `исполнитель` и `доработчик` пишут полный отчёт в файл, путь к которому указан в задании: что сделано, какие проверки запускались с командами и результатами, отклонения от спеки, сомнения. В ответе возвращают только статус и одну строку сути:
  - `DONE` – сделано;
  - `DONE_WITH_CONCERNS` – сделано, но есть сомнения: прочитать их в отчёте до проверки;
  - `NEEDS_CONTEXT` – не хватает информации: дополнить задание и запустить роль заново;
  - `BLOCKED` – выполнить невозможно: если проблема в спеке, вернуться к этапу 1 или 2.

## Тесты

- Прямое указание пользователя создать новые тесты или тестовые случаи выполнять и для существующего, и для нового кода, в том числе если оно дано во время работы. Оно имеет приоритет над ограничениями по умолчанию ниже; учитывать его в актуальных спеке и заданиях, не отказывать из-за того, что случай не относится к особо сложным или ошибкам ревью.
- По умолчанию при изменении существующего кода по заданию пользователя актуализировать существующие тесты под согласованное новое поведение, не создавать новые тесты и тестовые случаи, кроме обязательного покрытия исправленной ошибки ревью по правилу ниже.
- При падении теста сначала тщательно изучить затронутый код, связанные вызовы и причину сбоя: проверить, не внесена ли ошибка и соответствует ли реализация заданию. Ошибку в коде исправлять в коде. Менять тест разрешено только после подтверждения, что его ожидания устарели из-за согласованного изменения поведения; не ослаблять проверки, не удалять и не отключать тест ради успешного прогона.
- При написании нового кода создавать тесты по прямому указанию пользователя, для особо сложных случаев по усмотрению модели либо для обязательного покрытия исправленной ошибки ревью. По умолчанию в остальных случаях нового кода тесты не создавать.
- После исправления ошибки, найденной ревьюером или экспертом, обязательно покрыть тестами все сценарии проявления этой ошибки, включая применимые крайние случаи. Это исключение действует и для существующего, и для нового кода: при необходимости создавать новые тесты и тестовые случаи; проверки должны воспроизводить ошибку до исправления и проходить после него.
- Эти правила включать в спеки и задания исполнителю и доработчику; ревьюерам и экспертам передавать их как критерии проверки. В отчёте указывать причины падений, выводы проверки кода, обоснование изменения ожиданий и покрытые сценарии исправленных ошибок ревью. Ограничение на длительные тяжёлые прогоны сохраняется; незапущенные проверки явно отмечать, не выдавая их за успешные.

## Каталог прогона и журнал

- В начале создать каталог прогона в репозитории спек `SPECS_REPO=/workspace/vscode/raven/man4llm` скриптом `scripts/run-dir.sh "${MAIN_DIR}" "${SPECS_REPO}" <краткое-имя> [<тема>]`, где `MAIN_DIR` – основная рабочая копия проекта, а не `WT_DIR`. Скрипт печатает путь `RUN_REL` относительно корня репозитория спек: `<владелец>/<репо>/[<тема>/]<ГГГГММДД>-<NN>-<краткое-имя>`, где `<владелец>` – `basename(dirname(путь-репо))`, `<репо>` – `basename(путь-репо)`, `путь-репо` – вывод `git rev-parse --show-toplevel` в `MAIN_DIR` (для `/workspace/vscode/raven/container-images` получится `raven/container-images/…`), `NN` – следующий свободный номер за день, а необязательная тема – подкаталог по примеру соседних спек. Абсолютный путь каталога прогона – `RUN_DIR=${SPECS_REPO}/${RUN_REL}`. Все артефакты хранить в нём:
  - `task.md` – моё исходное задание дословно;
  - `ledger.md` – журнал;
  - `context-state.md` – последнее состояние управления контекстом: телеметрия, выбранный порог и запас, текущий этап, пути к заданиям и точный следующий шаг;
  - `assignment-<роль>-<этап>-<N>-<модель>.md` – полное задание подсессии с моделью, входными и выходными путями; для повторов и замен использовать отдельные файлы с суффиксом, прежние не перезаписывать;
  - `questions-<N>.md` – готовые вопросы и варианты для следующего вызова `ask_user`;
  - `facts-<N>.md` – найденные факты;
  - `facts-<N>-<модель>.md` – факты одного скаута из пары;
  - `decisions.md` – вопросы и мои ответы на них;
  - `spec-v<N>.md` – версии спеки;
  - `spec-v<N>-files/` – вложения спеки: готовые файлы по путям относительно `WT_DIR`, по правилам этапа 2;
  - `fix-spec-<N>.md` – спеки исправлений;
  - `fix-spec-<N>-files/` – вложения спеки исправлений по той же схеме;
  - `report-<роль>-<N>.md` – отчёты ролей;
  - `plan-<роль>-<этап>-<N>-<модель>.md` – независимые планы ревьюеров и экспертов;
  - `review-<этап>-<N>-<модель>.md` – вердикты и замечания ревьюеров и экспертов;
  - `remarks-<этап>-<N>.md` – оставшиеся замечания перед компактом контекста;
  - `diff-<N>.patch` – пакеты для ревью.
- В именах файлов `<этап>` – номер этапа: `2` – ревью спеки, `3` – доработка, `4` – финальное ревью и эксперты. `<модель>` – часть id модели из раздела ролей между `/` и `:`, например `claude-haiku-5-5`. `<N>` в `plan-…`, `review-…` и `remarks-…` – номер раунда цикла: в каждом новом раунде он увеличивается, прежние файлы не перезаписываются. Перед повтором после `BLOCKED` в том же раунде оркестратор переименовывает файл замечаний этой модели и её файл плана этого раунда, если он есть, добавляя к имени перед `.md` суффикс `-blocked`, а новые план и вердикт пишутся под прежними именами.
- Журнал только дописывать. Первая строка – `# spec-pipeline – <задача одной строкой>`, дальше по строке на событие:
  - текущий этап и раунд;
  - прочитанный файл `references/`;
  - запуск роли: роль, id подсессии, путь к заданию;
  - ошибка лимитов модели и продолжение без неё;
  - версия спеки: путь и SHA256;
  - вердикт ревьюера и краткий список замечаний;
  - голосование по замечанию: голоса и решение;
  - снимок рабочего дерева: имя, хеш и после чего сделан;
  - решение оркестратора: что решено, почему и чем грозит ошибка;
  - выбор варианта доработчика: сложность, модель и краткая причина;
  - точка компакта: следующий шаг, порог и причина его выбора, доступная телеметрия вызова и продолжения.
- После сжатия контекста сначала прочитать журнал и доверять ему и git, а не собственной памяти. Завершённые по журналу шаги не повторять.

## Управление контекстом

- Условный компакт выполнять инструментом `compact_context` до начала каждой следующей самостоятельной работы, а не после её запуска: перед отдельной подсессией или параллельной пачкой любых ролей, включая голосования и повторы; перед сведением отчётов скаутов, написанием или переработкой спеки, разбором результатов и проверкой diff оркестратором; перед раундом вопросов через `ask_user` и итоговой проверкой с коммитом. Переходы между этапами и вопрос после 33 раундов тоже являются такими точками. Речь о блоках работы, не о каждом чтении файла или вызове инструмента.
- Первую точку выполнять после создания `RUN_DIR`, подготовки `WT_DIR` и записи `MAIN0`, до первых скаутов. Если подготовка остановилась до создания этих артефактов, сразу задать вопрос через `ask_user`, не пытаться делать компакт с несуществующими путями.
- Параллельная пачка считается одной работой: один условный компакт перед всей пачкой, без компактов между её участниками. После запуска записать id подсессий и на точке ожидания вызвать `yield_to_subsessions`; компакт после запуска ради самого ожидания не выполнять. Совпавшие точки, например переход этапа и запуск исполнителя, обслуживать одним вызовом. Подготовка контрольной записи и восстановление после компакта новых точек не создают.
- До вызова отдельными предыдущими ходами сохранить всё нужное для продолжения:
  - оставшиеся замечания полностью в `remarks-<этап>-<N>.md`, если они есть; перед новой точкой того же раунда дополнять файл, не теряя прежних замечаний и решений;
  - полные задания следующей пачки в `assignment-…` или вопросы в `questions-<N>.md`; для локальной работы – входные пути, ожидаемый результат и критерий завершения в `context-state.md`;
  - в `context-state.md` – последнюю доступную телеметрию, следующий порог, запас, текущий этап, точный следующий шаг и пути к его файлам; в журнал – этап, цикл, раунд, активные id подсессий и следующий шаг. Задание должно позволять после восстановления запустить именно подготовленную работу без повторного обсуждения;
  - закоммитить изменения каталога прогона в репозиторий спек скриптом `scripts/commit-specs.sh`.
- `minContextTokens` задавать явно и выбирать динамически. `222222` – стартовый ориентир, а не постоянный порог. Реальное максимальное окно брать из последнего ненулевого `contextWindow` расширения; не выдумывать размер окна и не считать, что изменение порога меняет окно модели. После смены модели прежний размер окна не использовать до получения новой телеметрии.
- Оставлять запас под следующую работу: её входные файлы и diff, чтение всех отчётов пачки, разбор замечаний, подготовку исправлений и следующей контрольной записи. При известном окне запас брать не меньше 20% окна, увеличивая его для крупных diff и пачек по наблюдаемому расходу. Порог не должен превышать `contextWindow` минус этот запас; при первом известном окне стартовый ориентир ограничить также 60% окна. Если даже после сжатия следующая работа не помещается, уменьшить блок работы и объём чтения, а не рассчитывать на переполнение.
- Использовать обратную связь расширения:
  - результат вызова содержит `tokens`, `minContextTokens`, `contextWindow`, `percent`; это состояние в момент вызова, не после сжатия. `skipped: true` с `reason: below-threshold` или `unknown` означает пропуск;
  - после завершившегося компакта продолжение содержит `tokensAtCall`, `percentAtCall`, `tokensBefore`, `percentBefore`, `tokensAfter`, `percentAfter`, `contextWindow`, `minContextTokens`; `tokensAfter` – оценка, а значения `null` не считать нулями. Для оценки экономии использовать `tokensBefore` и `tokensAfter`, а для роста между точками – сопоставимые значения без пересечения сжатия;
  - на следующую точку снижать порог, если предыдущая работа съела ожидаемый запас или приблизила контекст к пределу; повышать только если сжатия стали частыми и малоэффективными, а запаса под следующую работу достаточно. Причину и новый порог записывать. При недостатке телеметрии сохранять консервативный порог, не повышать его наугад;
  - полученную телеметрию дописать в журнал и обновить `context-state.md` до следующей контрольной записи; результат пропущенного вызова можно сохранить перед выполнением следующего шага, не создавая новую точку компакта.
- Вызвать `compact_context` единственным инструментом в сообщении. В `instructions` передать `RUN_DIR`, `WT_DIR`, путь проекта, этап, цикл и раунд, а также указание сохранить состояние из `context-state.md`. В `next` передать абсолютный путь к `SKILL.md` из атрибута `location` блока `<skill …>` и абсолютные пути к файлу текущего этапа и `references/review-cycle.md`, если текущий этап – 2 или 4, абсолютные `RUN_DIR` и `WT_DIR`, указание прочитать эти файлы скилла, затем `ledger.md`, `context-state.md` и файл замечаний, если он есть, и выполнить записанный следующий шаг без нового компакта в той же точке.
- Если вызов пропущен, сразу выполнить подготовленный следующий шаг. Не снижать порог и не повторять вызов в той же точке ради принудительного сжатия. Если компакт запланирован, немедленно закончить ход без других инструментов и сообщений, дождаться продолжения. После успешного сжатия или сообщения об ошибке продолжить записанный шаг; ошибку зафиксировать, а при нехватке запаса уменьшить блок работы. Если запуск сорвался из-за новых сообщений, сначала обработать их и сверить актуальность следующего шага. Повторный вызов разрешён только в следующей точке работы, не циклом в текущей.

## Скрипты

Скрипты лежат в `SKILL_DIR/scripts/`, принимают абсолютные пути и заменяют ручные команды git. При ненулевом коде возврата прочитать сообщение на stderr и действовать по правилам этапа, не повторять команду вручную.

- `run-dir.sh <MAIN_DIR> <SPECS_REPO> <краткое-имя> [<тема>]` – создаёт каталог прогона и печатает `RUN_REL`.
- `worktree.sh <MAIN_DIR> <слог репо> <слог задачи>` – проверяет, что основная рабочая копия чистая и `HEAD` не отсоединён, создаёт от `HEAD` ветку и worktree по правилам этапа 1 и печатает три строки: ветку, `WT_DIR` и `HEAD`. При ненулевом коде возврата остановиться и спросить меня.
- `snapshot.sh <каталог>` – печатает хеш дерева: снимок рабочего дерева без коммитов и без изменения индекса, неотслеживаемые файлы входят, игнорируемые – нет.
- `review-bundle.sh <WT_DIR> <FROM> <TO> <OUT>` – пишет в `OUT` пакет для ревью между снимками `FROM` и `TO`: `git diff --stat` и `git diff -U10`.
- `spec-files.sh <каталог вложений>` – печатает манифест вложений спеки строками `<SHA256> <путь>`.
- `commit-specs.sh <SPECS_REPO> <RUN_DIR>` – добавляет каталог прогона в индекс и коммитит только его: сообщение `add <RUN_REL> spec` для первого коммита каталога, `update <RUN_REL> spec` для остальных; без изменений ничего не коммитит и печатает `nothing to commit`.
- `commit-project.sh <WT_DIR> <сообщение> [<путь>…]` – единственный коммит в проект: без путей добавляет всё через `git add -A`, с путями – только их; печатает SHA и сообщение коммита.

Правила коммитов:

- коммитит только роль `оркестратор`: в проект – один итоговый коммит в `WT_DIR` на этапе 4, в репозиторий спек – после каждой подсессии роли, изменившей файлы в каталоге прогона, и в конце прогона;
- автор и коммитер – из раздела ролей, а не из `git config`; коммиты без криптоподписи; в коммит в репозиторий спек попадает только каталог прогона, чужие изменения там не трогать;
- добавлять `Co-Authored-By` и любые другие трейлеры с упоминанием моделей запрещено.
