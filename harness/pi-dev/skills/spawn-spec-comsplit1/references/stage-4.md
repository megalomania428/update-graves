# Этап 4. Финальное ревью

<!-- cspell:ignore коммита коммитер ревьюер ревьюера ревьюеры спеке -->
<!-- markdownlint-disable-file MD013 -->

- Сначала финальное ревью проводит вся компашка `ревьюер`: подготовить задания и провести раунд по `review-cycle.md`. Передать пути к файлам:
  - `task.md` – моё исходное задание;
  - `decisions.md` – вопросы и мои ответы;
  - одобренную спеку с решениями по вопросам, её каталоги вложений и правок и diff полных замен;
  - спеки исправлений с теми же их файлами, если были;
  - сводный `facts-<N>.md`;
  - diff от `T0` до текущего снимка, собранный `scripts/review-bundle.sh`.
- При первом финальном ревью требовать от каждого ревьюера до открытия спек и diff выписать по `task.md` и `decisions.md` нумерованный список требований и крайних случаев в `plan-ревьюер-4-<N>-<модель>.md`.
- Задача роли `ревьюер` – проверить результат по `task.md` и `decisions.md`, а не по спеке: каждое требование свести к строке diff или к замечанию «не реализовано», искать сценарии поломки и изменения вне scope. Соответствие спеке вторично.
- Ошибки финального ревью, скорее всего, сложные и неочевидные: по принятым замечаниям написать `fix-spec-<N>.md` с обязательным тестовым покрытием всех сценариев исправляемой ошибки по разделу «Тесты» `SKILL.md` и выполнить её ролью `исполнитель` по `stage-3.md`, включая цикл доработки. Принятые замечания компашки и экспертов исправляются только так.
- Изменение для повторного ревью – diff от снимка прошлого ревью до текущего.
- Когда цикл компашки пройден по `review-cycle.md`, подготовить задания паре `эксперт`, выполнить условный компакт и запустить пару: она один раз проверяет весь diff от `T0` с теми же файлами и задачей, что у компашки. До открытия спек и diff каждая модель пишет список требований и крайних случаев в `plan-эксперт-4-<N>-<модель>.md`, а каждое замечание помечает `CRITICAL` или `MINOR`.
- Замечания экспертов разбирать так:
  - принятые исправлять по общему правилу: `fix-spec-<N>.md` → `исполнитель` → проверка по этапу 3;
  - отклонённые оркестратором сразу выносить на голосование, эксперта повторно не вызывать: вся компашка получает замечание и причину отклонения и отвечает одной строкой `AGREE` или `DISAGREE`, четвёртый голос – оркестратора. Голосуют работающие ревьюеры компашки и оркестратор, недоступных по лимитам не ждать. Решает большинство поданных голосов, при равенстве – оркестратор: при отклонении замечание закрыто, иначе исправляется по общему правилу. Решение и голоса записать в журнал;
  - `MINOR` после исправления проверяет компашка по diff исправления;
  - `CRITICAL` после исправления один раз перепроверяет только нашедшая его модель-эксперт: её замечания плюс diff исправления. Если `CRITICAL` нашли обе модели, перепроверяют обе. Если нашедшая модель недоступна, его проверяют компашка и оркестратор в общем лимите раундов;
  - если после перепроверки `CRITICAL` остался `NOT ADDRESSED`, дальше его проверяют компашка и оркестратор в общем лимите раундов. Повторно экспертов для перепроверки не вызывать.
- Кроме вопроса после 33 раунда, недоступности всех моделей роли, повторного `BLOCKED` или недостающего вне списка передаваемых файлов и расхождения снимка основной рабочей копии, других поводов спрашивать меня по ревью нет.
- Цикл продолжается, пока довольны все, включая роль `оркестратор`.
- После одобрения итога сделать в `WT_DIR` один коммит всех изменений командой `scripts/commit-project.sh "${WT_DIR}" "${MESSAGE}" [<путь>…]`:
  - проверить `git -C "${WT_DIR}" status --short`: если там только файлы из одобренного diff от `T0` – запускать без путей, иначе перечислить только эти файлы поимённо, без установленных зависимостей и посторонних файлов;
  - сообщение в переменной `MESSAGE` – одна строка в стиле последних коммитов проекта из `git -C "${WT_DIR}" log --format=%s -15`;
  - автор, коммитер и запрет трейлеров – по разделу «Скрипты» `SKILL.md`.
- Слияние ветки и удаление worktree выполняю я. В итоговом ответе мне указать `WT_DIR`, ветку и SHA коммита.
