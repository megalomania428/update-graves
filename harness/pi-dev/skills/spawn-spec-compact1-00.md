# Доработка через цепочку агентов

Задача передаётся аргументом команды и приходит в конце скилла как `User: …`.

## Роли

Модели задаются только в этом разделе, остальной текст ссылается на роли.

- `скаут` – основная `anthropic/claude-sonnet-5-5:medium` и вторая `openai-codex/gpt-6.1-sol:medium`: только исследование фактов для вопросов, без проверки выполнимости спеки. При ошибке лимитов одной работает другая. Ничего не изменяет, кроме своих файлов в каталоге прогона.
- `ревьюер` – компашка `openai-codex/gpt-6-luna:max`, `openai-codex/gpt-6.1-terra:medium`, `anthropic/claude-haiku-5-5:max` и `zai/glm-5.3-flash:low`: ревью спеки и финальное ревью, все одновременно. Если у кого-то ошибка лимитов, продолжать с оставшимися и записать это в журнал.
- `эксперт` – пара `anthropic/claude-fable-5-1:high` и `openai-codex/gpt-6-astra:high`: финальная проверка кода, только после одобрения компашкой `ревьюер`, обе одновременно. Если у одной ошибка лимитов, работает другая.
- `исполнитель` – `openai-codex/gpt-6.1-sol:medium`: первичное выполнение спеки и исправление ошибок финального ревью, `anthropic/claude-sonnet-5-5:medium`, если от первого прилетела ошибка лимитов.
- `доработчик` – для простых исправлений `anthropic/claude-haiku-5-5:max`, при ошибке лимитов `openai-codex/gpt-6-luna:max`; для сложных исправлений `openai-codex/gpt-6.1-sol:medium`, при ошибке лимитов `anthropic/claude-sonnet-5-5:medium`: исправление недоделок по итогам промежуточной проверки. Вариант выбирает оркестратор перед каждым запуском по правилам этапа 3; при недоступности обеих моделей выбранного варианта действует общее правило недоступности роли.
- `оркестратор` – текущая сессия: вопросы, допустимые автономные решения, сведение отчётов скаутов в своём контексте, спеки, разбор отчётов и diff, контроль Git и хешей, запуск остальных ролей, коммиты в репозиторий спек, создание worktree проекта и один итоговый коммит в нём. Код проекта самостоятельно не правит, спеку не применяет, проверки, тесты, симуляции и прототипы не запускает, в том числе во временных каталогах и на этапах 3–4. Чтение diff и отчётов, контроль Git и хешей, подготовка разрешённых каталогов и ведение прогона сохраняются. Автор коммитов: `ORCH_NAME='Moderator'`, `ORCH_EMAIL='<moderator@models.dev>'`

## Общие правила

- Все роли запускать через `spawn_subsession`, передавая модель роли в параметре `model`. Перед каждым запуском отдельной подсессии или параллельной пачки выполнять условный компакт по разделу «Управление контекстом»; это относится также к повтору после `BLOCKED`, замене модели из-за лимитов, голосованию, консультациям, перепроверкам и необходимым техническим прогонам всей работающей компашки ревьюеров.
- Все вопросы пользователю, включая уточнения, согласования, продолжение после 33 раундов и остановки по ошибкам, задавать только через `ask_user`. Текстовое сообщение с вопросом вместо вызова инструмента запрещено. Готовые независимые вопросы объединять в один вызов; вызывать `ask_user` единственным инструментом в сообщении и последним действием хода, затем ждать ответа. В каждом вопросе, включая остановки, давать собственную рекомендацию с причиной. Перед блоком искать прецеденты по разделу «Автономный режим»: при совпадении добавлять ссылку на запись и дату, при расхождении показывать рекомендацию с причиной расхождения и позицию прецедента со ссылкой и датой; если применимого прецедента нет, так и указывать. Оставленные без ответа вопросы считать открытыми, не подставлять рекомендуемый вариант молча. Повторять блок только при полном отсутствии ответов на все его вопросы. Любой содержательный ответ хотя бы на один вопрос исключает повтор исходного блока целиком и уже отвеченных вопросов; только оставшиеся открытые вопросы можно адресно вынести в `ask_user` со ссылкой на номер исходного блока и номера его вопросов. Связь сохранять в артефактах и при получении ответов в `decisions.md`, фиктивных ответов не добавлять. Каждое такое обращение заканчивает ход и ожидает настоящего ответа по общему правилу, без немедленной бесконечной переотправки. В автономном режиме допустимую развилку можно закрыть отдельным записанным решением, но обязательный вопрос остаётся блокирующим.
- Если недоступны все модели роли, остановиться и спросить меня.
- Работа идёт на лэптопе: в каждой спеке для любой роли запрещать длительные тяжёлые проверки и тесты без явного разрешения пользователя только на указанные команды и объём. Прямое указание передавать дословно, разрешение самостоятельно не расширять.
- В каждой спеке для любой роли явно запрещать инструменты `spawn_*`, чтобы роль работала в одиночку.
- С файлами проекта все роли работают только в worktree `WT_DIR` из этапа 1, а свои файлы пишут по путям из задания в каталог прогона. Дополнительные рабочие каталоги и worktree допускаются только для операций, прямо предусмотренных инструкциями проекта (`AGENTS.md`, `CLAUDE.md` и подобными); их подготовку и очистку обеспечивает оркестратор по этим инструкциям. Отдельное исключение – собственные временные клоны ревьюеров для необходимого технического прогона по правилам этапа 2, включая их действие на этапах 3–4; скаутам оно не предоставляется. PI WEB запускает подсессии в каталоге оркестратора, поэтому в каждом задании для любой роли указывать:
  - абсолютный `WT_DIR` и разрешённые дополнительные рабочие каталоги, если они нужны;
  - команды проекта выполнять через `cd "${WT_DIR}" &&` или `git -C "${WT_DIR}"`; для операций в других разрешённых каталогах явно задавать соответствующий абсолютный рабочий каталог;
  - пути к файлам писать абсолютными; файлы проекта изменять внутри `WT_DIR`, а ревьюерам при техническом прогоне – только в собственном временном клоне вместо реального `WT_DIR`; операции в дополнительных каталогах выполнять только в пределах, разрешённых инструкциями проекта и ролью;
  - основную рабочую копию проекта и общие рабочие копии внешних репозиториев не трогать;
  - установка зависимостей (`node_modules`, venv и подобное) разрешена внутри `WT_DIR` либо в дополнительных каталогах, прямо назначенных для этого инструкциями проекта; при техническом прогоне ревьюера – внутри его собственного временного клона, не реального `WT_DIR`.
- В каждой спеке для ролей `исполнитель` и `доработчик` указывать: веток и worktree самостоятельно не создавать, использовать только подготовленные оркестратором рабочие каталоги; в проекте и дополнительных worktree ничего не коммитить.
- Репозитории GitHub все роли, включая `оркестратор`, изучают только локально: сначала искать клон в `/workspace/github/<репо>`, а если его нет – выполнить `git -C /workspace/github clone https://github.com/<владелец>/<репо>`. Исключение – репозитории больше гигабайта: перед клонированием сверить размер в КБ через `curl -s https://api.github.com/repos/<владелец>/<репо> | jq .size`, и при значении больше `1048576` не клонировать, а изучать удалённо. В каждой спеке для любой роли указывать это правило явно.
- Артефакты передавать ролям путями к файлам в каталоге прогона, а не вставлять их содержимое в текст задания.
- Каждый цикл с ролями – ревью спеки, доработка, финальное ревью – не больше 33 раундов подряд, лимит считается для каждого цикла отдельно. После 33 раунда с незакрытыми замечаниями сохранить их, выполнить условный компакт по разделу «Управление контекстом», затем через `ask_user` показать оставшиеся замечания и спросить, продолжать или нет. Это ограничение числа раундов, а не периодичность компакта; без разрешения следующий раунд не запускать.
- При каждом обращении к ролям `ревьюер` и `эксперт`:
  - писать максимально кратко, но достаточно для проверки, и требовать таких же кратких ответов;
  - передавать только `task.md`, актуальный `decisions.md` со всеми уже полученными ответами, сводный `facts-<N>.md`, `autonomous-decisions.md`, если он есть, спеку, спеки исправлений и diff, а при повторной проверке, перепроверке, консультации и голосовании – ещё уже существующие файлы `review-<этап>-<N>-<модель>.md`, `recheck-<этап>-<N>-<K>-<модель>.md` и `consult-<этап>-<N>-<K>-<модель>.md` с обсуждаемыми замечаниями или доводами, включая уникальные review/recheck технических прогонов по правилам каталога прогона. До первого ответа при отсутствии `decisions.md` явно сообщать, что пользовательских ответов пока нет, и не требовать несуществующий файл. Автономные решения учитывать в пределах полномочий оркестратора; приоритет прямых указаний пользователя сохраняется. Решения оркестратора и причины отклонения пишутся в задании одной строкой на замечание и пересказом рассуждений не считаются. Остальные файлы не передавать, рассуждения оркестратора не пересказывать, требовать читать из каталога прогона только переданные файлы;
  - не сообщать, кто и какой моделью написал спеку или код, не упоминать роли и не оценивать автора ни в плюс, ни в минус: подавать как «спека на проверку» или «изменения на проверку»;
  - ставить задачу как поиск ошибок: считать, что ошибка есть, и в каждом замечании указывать конкретный сценарий поломки. Минимального числа замечаний не требовать;
  - остальные инструменты разрешены, но без длительных тяжёлых тестов;
  - не подсказывать заранее, какие замечания выдавать не нужно;
  - при обычном ревью план писать в `plan-<роль>-<этап>-<N>-<модель>.md`, вердикт и замечания – в `review-<этап>-<N>-<модель>.md`, а в ответе возвращать только вердикт и путь к файлу замечаний. Замечания и причину `BLOCKED` оркестратор читает из этого файла. Консультации и перепроверки имеют отдельные форматы и файлы по соответствующим разделам; новые планы для них не требуются, формат обычного ревью на них не распространяется;
  - при обычном ревью требовать в файле замечаний строго формат:
    - первая строка – вердикт `APPROVED`, `REVISE` или `BLOCKED`;
    - дальше нумерованные замечания, по одной строке на каждое, с `путь:строка`, где применимо;
    - при `APPROVED` вместо замечаний одна строка: какие сценарии поломки проверены и почему они не срабатывают;
    - при `BLOCKED` одной строкой указать, чего не хватает для проверки.
- Роли `исполнитель` и `доработчик` пишут полный отчёт в файл, путь к которому указан в задании: что сделано, какие проверки запускались с командами и результатами, отклонения от спеки, сомнения. В ответе возвращают только статус и одну строку сути:
  - `DONE` – сделано;
  - `DONE_WITH_CONCERNS` – сделано, но есть сомнения: прочитать их в отчёте до проверки;
  - `NEEDS_CONTEXT` – не хватает информации: дополнить задание и запустить роль заново;
  - `BLOCKED` – выполнить невозможно: если проблема в спеке, вернуться к этапу 1 или 2.

## Автономный режим

- До первого учитываемого раунда выбрать порог отсутствия пользователя – 2 или 3 – и записать его в журнал. Раунд здесь – завершённый раунд скаутов или вопросов этапа 1 и полный раунд ревью этапа 2; этапы считаются подряд, одна пара скаутов – один раунд. Если последние выбранные 2–3 раунда подряд прошли без `ask_user` и сообщений пользователя, считать пользователя отсутствующим и перейти к автономному режиму. Вызов `ask_user` или любое сообщение пользователя сбрасывает счёт на ноль; раунд с таким событием не увеличивает счёт. На этапах 1–2 сообщение пользователя возвращает режим присутствия до нового достижения порога. Служебные уведомления подсессий сообщениями пользователя для этого счёта не являются.
- Если этап 2 закончился раньше порога, перейти к автономному режиму при его завершении; на этапах 3–4 режим автономный независимо от прежнего счёта. Сообщения пользователя на этих этапах обязательно учитывать, но они сами по себе не отменяют режим. Прямое указание пользователя о том, когда спрашивать, важнее автоматического перехода.
- Компакт, ожидание, повтор роли в том же раунде и смена модели не являются новыми раундами и не сбрасывают счёт. Порог, счёт, режим и последний учтённый раунд сохранять в `context-state.md`, события счёта и переходы – в журнале. Не смешивать этот счёт с лимитом 33 раундов каждого цикла.
- В автономном режиме обязательно спрашивать через `ask_user` до зависимой работы при противоречии явных решений пользователя в `task.md`, `decisions.md` и последующих сообщениях; перед необратимым действием независимо от каталога либо действием, видимым за пределами `WT_DIR` и каталога прогона; при недоступности всех моделей роли; при повторном `BLOCKED`, недостающем вне разрешённых входов и другой неустранимой блокировке; при нарушении изоляции, расхождении снимка основной рабочей копии или невозможности безопасно подготовить worktree; при исчерпании лимита раундов. Штатный один повтор `BLOCKED` и замены по лимитам сохраняются. Уже прямо разрешённые конкретные действия не требуют повторного разрешения: источник – прямое задание, ответы или сообщения пользователя либо явно разрешённые конкретные операции инструкций, действующих в этом задании. Расплывчатая ссылка на инструкции не разрешает внешние или необратимые операции; расширять конкретное разрешение самостоятельно нельзя. Обязательные вопросы не закрываются молчанием, прецедентом, консультацией или голосованием.
- Остальные развилки в автономном режиме оркестратор решает самостоятельно, не отменяя и не сужая прямых указаний пользователя и не расширяя разрешённые каталоги или полномочия ролей. Сначала искать решение без отступления от задания, явных решений и инструкций проекта. Пока пользователь на месте, развилки этапов 1–2 выносить на вопросы.
- Для каждого автономного решения искать применимые прецеденты прошлых прогонов в `SPECS_REPO`: просматривать датированные каталоги с `task.md` и `decisions.md` от новых к старым для поиска кандидатов, затем читать полный контекст найденных применимых вопросов и ответов, а не все файлы всех прогонов. Свежесть определять по достоверно указанной дате именно данного решения или ответа; если её нет, использовать дату прогона как явно обозначенную резервную дату, сохраняя источник даты в записи основания. Дата изменения файла и дата другой записи не используются. Имя каталога не перевешивает известную дату ответа: не прекращать поиск применимых более свежих решений только потому, что первый найденный каталог новее по имени, и не вводить произвольный лимит поиска. Более свежее решение важнее старого; только при одинаковой дате следующий фактор – близость проекта, прежде всего тот же проект. Близость проекта не может перевесить более свежую дату применимого решения. Текущий прогон не является прошлым прецедентом, совпадение слов задания не является ответом пользователя, чужое автономное решение не выдавать за такой ответ. Сохранять ссылку на конкретную запись, `RUN_REL` и дату; при отсутствии применимого прецедента записывать собственное основание.
- Спорные толкования и необходимые отступления от инструкций проекта до решения обсуждать со всеми работающими ревьюерами, без экспертов: передать вопрос, `task.md`, актуальный `decisions.md` со всеми уже полученными ответами; до первого ответа при отсутствии файла явно указать отсутствие пользовательских ответов и файл не требовать. Сводные факты и автономные решения передавать при их наличии; спеку, diff и относящиеся к вопросу отчёты передавать только если они уже существуют и нужны для обсуждения. Получить доводы за и против в отдельных `consult-<этап>-<N>-<K>-<модель>.md`. В ответе ревьюера – только `DONE` или `BLOCKED` и путь; в файле – доводы по существу либо `BLOCKED` с причиной, без плана и формального вердикта ревью. Перед пачкой выполнить условный компакт. Решение принимает оркестратор по существу доводов, не голосованием, и отвечает в журнале на каждый довод. Для `BLOCKED` действуют общие правила. Консультация не отменяет обязательного вопроса и прямого запрета пользователя; существующее голосование по `DISPUTED` сохраняется, но конфликт явных решений голосованием не разрешается.
- Каждое автономное решение записывать отдельно в `autonomous-decisions.md`: двузначный номер, этап и раунд, вопрос, решение, основание, ссылки и даты прецедентов или их отсутствие, консультационные доводы и существенные риски. Решение против большинства доводов отмечать «вопреки ревьюерам». Передавать актуальные решения всем затронутым ролям; изменение контракта одобренной спеки требует новой версии и ревью. При новом прямом указании пересматривать затронутые автономные решения с сохранением истории, не продолжать устаревшее задание.
- При завершении и любой остановке прогона полностью перечислять все записи `autonomous-decisions.md` по одной строке в разделе «Автономные решения», с путём к файлу; если записей нет, явно указывать это. При остановке полный перечень выводить отдельным текстовым сообщением перед `ask_user`, при необходимости несколькими сообщениями; это сообщение не должно содержать вопросов. Сами вопросы задавать только через `ask_user`, не пытаться вместить перечень в ограниченные поля формы и не откладывать его до успешного финала. В `decisions.md` записывать только вопросы и дословные ответы пользователя, не выдавать автономные решения за пользовательские.

## Тесты

- Прямое указание пользователя создать новые тесты или тестовые случаи выполнять и для существующего, и для нового кода, в том числе если оно дано во время работы. Оно имеет приоритет над ограничениями по умолчанию ниже; учитывать его в актуальных спеке и заданиях, не отказывать из-за того, что случай не относится к особо сложным или ошибкам ревью.
- По умолчанию при изменении существующего кода по заданию пользователя актуализировать существующие тесты под согласованное новое поведение, не создавать новые тесты и тестовые случаи, кроме обязательного покрытия исправленной ошибки ревью по правилу ниже.
- При падении теста сначала тщательно изучить затронутый код, связанные вызовы и причину сбоя: проверить, не внесена ли ошибка и соответствует ли реализация заданию. Ошибку в коде исправлять в коде. Менять тест разрешено только после подтверждения, что его ожидания устарели из-за согласованного изменения поведения; не ослаблять проверки, не удалять и не отключать тест ради успешного прогона.
- При написании нового кода создавать тесты по прямому указанию пользователя, для особо сложных случаев по усмотрению модели либо для обязательного покрытия исправленной ошибки ревью. По умолчанию в остальных случаях нового кода тесты не создавать.
- После исправления ошибки, найденной ревьюером или экспертом, обязательно покрыть тестами все сценарии проявления этой ошибки, включая применимые крайние случаи. Это исключение действует и для существующего, и для нового кода: при необходимости создавать новые тесты и тестовые случаи; проверки должны воспроизводить ошибку до исправления и проходить после него.
- Эти правила включать в спеки и задания исполнителю и доработчику; ревьюерам и экспертам передавать их как критерии проверки. В отчёте указывать причины падений, выводы проверки кода, обоснование изменения ожиданий и покрытые сценарии исправленных ошибок ревью. Ограничение на длительные тяжёлые прогоны сохраняется; незапущенные проверки явно отмечать, не выдавая их за успешные.

В именах файлов `<этап>` – номер этапа: `1` – исследование и вопросы, `2` – ревью спеки, `3` – доработка, `4` – финальное ревью и эксперты. `<модель>` – часть id модели из раздела ролей между `/` и `:`, например `claude-haiku-5-5`. `<N>` в `plan-…`, `review-…` и `remarks-…` – номер раунда цикла: в каждом новом раунде он увеличивается, прежние файлы не перезаписываются. Перед повтором после `BLOCKED` в том же раунде оркестратор переименовывает файл замечаний этой модели и её файл плана этого раунда, если он есть, добавляя к имени перед `.md` суффикс `-blocked-<K>`, а новые план и вердикт пишутся под прежними именами. `<K>` – следующий свободный двузначный номер попытки соответствующего обращения в данном раунде или версии; консультации и перепроверки прежние файлы не перезаписывают. Номер раунда в имени перепроверки ссылается на исходное замечание, а её место в лимите цикла отдельно фиксируется в журнале.

## Управление контекстом

- Условный компакт выполнять инструментом `compact_context` до начала каждой следующей самостоятельной работы, а не после её запуска: перед отдельной подсессией или параллельной пачкой любых ролей, включая голосования, консультации, перепроверки, необходимые технические прогоны всей работающей компашки ревьюеров и повторы; перед сведением отчётов скаутов, написанием или переработкой спеки, разбором результатов и проверкой diff оркестратором; перед раундом вопросов через `ask_user` и итоговой проверкой с коммитом. Переходы между этапами и вопрос после 33 раундов тоже являются такими точками. Речь о блоках работы, не о каждом чтении файла или вызове инструмента.
- Первую точку выполнять после создания `RUN_DIR`, подготовки `WT_DIR` и записи `MAIN0`, до первых скаутов. Если подготовка остановилась до создания этих артефактов, сразу задать вопрос через `ask_user`, не пытаться делать компакт с несуществующими путями.
- Параллельная пачка считается одной работой: один условный компакт перед всей пачкой, без компактов между её участниками. После запуска записать id подсессий и на точке ожидания вызвать `yield_to_subsessions`; компакт после запуска ради самого ожидания не выполнять. Совпавшие точки, например переход этапа и запуск исполнителя, обслуживать одним вызовом. Подготовка контрольной записи и восстановление после компакта новых точек не создают.
- До вызова отдельными предыдущими ходами сохранить всё нужное для продолжения:
  - оставшиеся замечания полностью в `remarks-<этап>-<N>.md`, если они есть; перед новой точкой того же раунда дополнять файл, не теряя прежних замечаний и решений;
  - полные задания следующей пачки в `assignment-…` или вопросы в `questions-<N>.md`; для локальной работы – входные пути, ожидаемый результат и критерий завершения в `context-state.md`;
  - в `context-state.md` – последнюю доступную телеметрию, следующий порог, запас, точный следующий шаг и пути к его файлам, режим автономности, порог отсутствия, счёт и последний учтённый раунд; в журнал – этап, цикл, раунд, активные id подсессий и следующий шаг. Задание должно позволять после восстановления запустить именно подготовленную работу без повторного обсуждения;
  - закоммитить изменения каталога прогона в репозиторий спек, не создавать пустой коммит.
- `minContextTokens` задавать явно и выбирать динамически. `222222` – стартовый ориентир, а не постоянный порог. Реальное максимальное окно брать из последнего ненулевого `contextWindow` расширения; не выдумывать размер окна и не считать, что изменение порога меняет окно модели. После смены модели прежний размер окна не использовать до получения новой телеметрии.
- Оставлять запас под следующую работу: её входные файлы и diff, чтение всех отчётов пачки, разбор замечаний, подготовку исправлений и следующей контрольной записи. При известном окне запас брать не меньше 20% окна, увеличивая его для крупных diff и пачек по наблюдаемому расходу. Порог не должен превышать `contextWindow` минус этот запас; при первом известном окне стартовый ориентир ограничить также 60% окна. Если даже после сжатия следующая работа не помещается, уменьшить блок работы и объём чтения, а не рассчитывать на переполнение.
- Использовать обратную связь расширения:
  - результат вызова содержит `tokens`, `minContextTokens`, `contextWindow`, `percent`; это состояние в момент вызова, не после сжатия. `skipped: true` с `reason: below-threshold` или `unknown` означает пропуск;
  - после завершившегося компакта продолжение содержит `tokensAtCall`, `percentAtCall`, `tokensBefore`, `percentBefore`, `tokensAfter`, `percentAfter`, `contextWindow`, `minContextTokens`; `tokensAfter` – оценка, а значения `null` не считать нулями. Для оценки экономии использовать `tokensBefore` и `tokensAfter`, а для роста между точками – сопоставимые значения без пересечения сжатия;
  - на следующую точку снижать порог, если предыдущая работа съела ожидаемый запас или приблизила контекст к пределу; повышать только если сжатия стали частыми и малоэффективными, а запаса под следующую работу достаточно. Причину и новый порог записывать. При недостатке телеметрии сохранять консервативный порог, не повышать его наугад;
  - полученную телеметрию дописать в журнал и обновить `context-state.md` до следующей контрольной записи; результат пропущенного вызова можно сохранить перед выполнением следующего шага, не создавая новую точку компакта.
- Вызвать `compact_context` единственным инструментом в сообщении. В `instructions` передать `RUN_DIR`, `WT_DIR`, путь проекта, этап, цикл и раунд, а также указание сохранить состояние из `context-state.md`. В `next` передать абсолютный путь к этому скиллу из атрибута `location` блока `<skill …>`, абсолютные `RUN_DIR` и `WT_DIR`, указание прочитать скилл, затем `ledger.md`, `context-state.md`, `autonomous-decisions.md` и файл замечаний, если они есть, и выполнить записанный следующий шаг без нового компакта в той же точке.
- Если вызов пропущен, сразу выполнить подготовленный следующий шаг. Не снижать порог и не повторять вызов в той же точке ради принудительного сжатия. Если компакт запланирован, немедленно закончить ход без других инструментов и сообщений, дождаться продолжения. После успешного сжатия или сообщения об ошибке продолжить записанный шаг; ошибку зафиксировать, а при нехватке запаса уменьшить блок работы. Если запуск сорвался из-за новых сообщений, сначала обработать их и сверить актуальность следующего шага. Повторный вызов разрешён только в следующей точке работы, не циклом в текущей.

## Коммиты в репозиторий спек

- Коммитит только роль `оркестратор`: в проект – только один итоговый коммит в `WT_DIR` из этапа 4, а в репозиторий спек – после каждой подсессии роли, изменившей файлы в каталоге прогона, и в конце прогона.
- Автор и коммитер – из раздела ролей, а не из `git config`. Коммит без криптоподписи.
- В коммит попадает только каталог прогона, чужие изменения в репозитории спек не трогать.
- Сообщение первого коммита – `add ${RUN_REL} spec`, остальных – `update ${RUN_REL} spec`.
- Добавлять `Co-Authored-By` и любые другие трейлеры с упоминанием моделей запрещено.

```bash
git -C "${SPECS_REPO}" add -- "${RUN_DIR}"
GIT_AUTHOR_NAME="${ORCH_NAME}" GIT_AUTHOR_EMAIL="${ORCH_EMAIL}" \
  GIT_COMMITTER_NAME="${ORCH_NAME}" GIT_COMMITTER_EMAIL="${ORCH_EMAIL}" \
  git -C "${SPECS_REPO}" commit --no-gpg-sign -m "update ${RUN_REL} spec" -- "${RUN_DIR}"
```

## Снимки рабочего дерева

Снимок фиксирует состояние рабочего дерева проекта без коммитов и без изменения индекса репозитория. Неотслеживаемые файлы попадают в снимок, игнорируемые – нет. Функция запускается в каталоге проекта и печатает хеш дерева:

```bash
snapshot() {
  local dir tree
  if ! dir="$(mktemp -d /tmp/pi-snapshot.XXXXXXXXXX)"; then
    return 1
  fi
  if [[ "${dir}" != /tmp/pi-snapshot.* || ! -d "${dir}" || -L "${dir}" ]]; then
    return 1
  fi
  if ! GIT_INDEX_FILE="${dir}/index" git read-tree HEAD ||
    ! GIT_INDEX_FILE="${dir}/index" git add -A ||
    ! tree="$(GIT_INDEX_FILE="${dir}/index" git write-tree)" ||
    [[ ! "${tree}" =~ ^([0-9a-f]{40}|[0-9a-f]{64})$ ]]; then
    rm -rf -- "${dir}" || return 1
    return 1
  fi
  if ! rm -rf -- "${dir}"; then
    return 1
  fi
  printf '%s\n' "${tree}"
}
```

Пакет для ревью между снимками `FROM` и `TO`:

```bash
{ git diff --stat "${FROM}" "${TO}"; git diff -U10 "${FROM}" "${TO}"; } > "${OUT}"
```

Снимки проекта и пакеты для ревью считаются в `WT_DIR`: `snapshot` и `git diff` запускаются в подоболочке `(cd "${WT_DIR}" && …)`. Исключения – `MAIN0` и контрольный снимок основной рабочей копии: для них `snapshot` запускается в `(cd "${MAIN_DIR}" && snapshot)`. Каждый вызов инструмента bash – новая оболочка, поэтому функцию `snapshot` определять в той же команде, где она вызывается. При каждом захвате оркестратор явно проверяет код возврата присваивания хеша и допустимость полного хеша дерева до его записи или назначения пачке; на `set -e` вызывающей оболочки и command substitution не полагаться. Ошибка любого шага, включая очистку собственного проверенного временного каталога, означает неуспех без выдачи хеша; зависимую работу остановить по общим правилам блокировок и изоляции. Не подставлять `HEAD` или старый хеш и не запускать ревьюеров на недостоверном дереве.

## Этап 1. Исследование и вопросы

- Кроме подготовки worktree ничего не изменять, только исследовать доработку.
- Сразу после записи `task.md`, до первых скаутов, подготовить worktree проекта:
  - если в основной рабочей копии `git status --short` не пуст или `HEAD` отсоединён – остановиться и спросить меня;
  - создать от `HEAD` ветку `BRANCH=<текущая ветка>-<слог задачи>` и worktree `WT_DIR=/workspace/jobs/wtr4sdd/<слог репо>-<текущая ветка без «-» и «/»>-<слог задачи>` командой `git -C "${MAIN_DIR}" worktree add -b "${BRANCH}" "${WT_DIR}" HEAD`, где `MAIN_DIR` – `путь-репо` основной рабочей копии из раздела «Каталог прогона и журнал»;
  - пример: репозиторий `update-graves`, ветка `updates-002`, задача «compact» → ветка `updates-002-cmp`, `WT_DIR=/workspace/jobs/wtr4sdd/ugra-updates002-cmp`;
  - если ветка или `WT_DIR` уже существуют, добавить к обоим одинаковый двузначный числовой суффикс `-02`, `-03`… – первый, при котором свободны и ветка, и `WT_DIR`, например `updates-002-cmp-02` и `/workspace/jobs/wtr4sdd/ugra-updates002-cmp-02`;
  - слог – короткое легко читаемое сочетание согласных и гласных из имени, существующее слово не обязательно: `ugra` из `update-graves`, `golci` или `glci` из `go-lib-ci`, `redo` из `report-docs`. Слог задачи образуется так же из краткого имени задачи;
  - записать в журнал `WT_DIR`, ветку и `HEAD`, сделать снимок основной рабочей копии командой `MAIN0="$(cd "${MAIN_DIR}" && snapshot)"`, определив функцию `snapshot` в той же оболочке, и записать его в журнал.
- Факты из кода и окружения у меня не спрашивать и самостоятельно не искать, чтобы беречь контекст оркестратора. Для поиска запускать роль `скаут` с заданием: ничего не изменять, найденное записать со ссылками `путь:строка`, вернуть одну строку. Пока идёт поиск, задавать вопросы, которые от него не зависят.
- Вид вопроса скаутам определять при постановке задания и записывать в журнал:
  - двое – обе модели роли `скаут` параллельно: вопросы на полноту («найди все использования», «где настраивается», «есть ли ещё»), любые вопросы, где ответ может быть «нет»;
  - один – только основная модель: точечные вопросы – версия пакета, сигнатура функции, содержимое конкретного файла. Результат сразу пишется в `facts-<N>.md`.
- Двое пишут каждый в свой `facts-<N>-<модель>.md`, затем оркестратор сам читает оба отчёта и в своём контексте сводит их в `facts-<N>.md` с пометкой у каждого факта: «подтверждено обоими», «только один» или «противоречие», сохраняя ссылки `путь:строка`. Отдельную подсессию для сведения не запускать. Если из пары отработал только один, скопировать его файл в `facts-<N>.md` и записать в журнал, что пара неполная.
- При сведении оркестратор точечно по `путь:строка` проверяет противоречия, утверждения «не найдено» и находки только одного скаута. При неполной паре находками одного скаута считаются все факты.
- Развилки выстраивать в дерево решений: каждое решение порождает зависящие от него.
- Вопросы задавать раундами через `ask_user`. В раунд включать все вопросы, предпосылки которых уже решены. Вопрос, зависящий от открытого в этом же раунде, откладывать на следующий.
- Каждый вопрос нумеровать, давать варианты ответа с объяснением каждого варианта и рекомендуемый вариант с причиной.
- Пока пользователь на месте по разделу «Автономный режим», каждую развилку выносить на вопрос и ждать ответа. При автономности допустимые развилки закрывает оркестратор по этому разделу; обязательные вопросы сохраняются.
- Этап закончен, когда в дереве не осталось открытых развилок и неявных допущений.
- Сразу после получения каждого ответа записывать в `decisions.md` соответствующий вопрос, текст выбранного варианта и ответ пользователя дословно, включая частичные ответы до завершения этапа. До первого ответа при отсутствии файла всем ревью и консультациям явно сообщать, что пользовательских ответов пока нет, и не требовать несуществующий `decisions.md`; остальные реально имеющиеся входы передавать по общим правилам. Фиктивные ответы не создавать. Рекомендации, рассуждения и автономные решения оркестратора туда не включать; последние записывать только в `autonomous-decisions.md`. В конце этапа сверить полноту записей, не откладывая первую запись до этого момента. Перед началом написания спеки этапа 2 выполнить условный компакт по разделу «Управление контекстом».

## Этап 2. Спека и её ревью

- Написать `spec-v<N>.md`, с которой справится слабая модель:
  - согласованные требования и решения, включая актуальные `autonomous-decisions.md` при наличии, с приоритетом прямых указаний пользователя;
  - вопросы и мои ответы на них;
  - код для вставки или замены;
  - пути файлов, номера строк в текущем коде и точное место вставки или замены;
  - проверки, которые нужно выполнить, и допустимые изменения тестов по разделу «Тесты», с учётом запрета длительных тяжёлых прогонов.
- Выполнимость спеки оценивают ревьюеры в своих замечаниях. Оркестратор спеку не применяет и проверок, тестов, симуляций и прототипов не запускает, в том числе во временных каталогах; разрешённые чтение diff и отчётов, контроль Git и хешей сохраняются на всех этапах. Скауты только исследуют факты; проверку выполнимости им не поручать.
- Технический прогон не является обязательной отдельной стадией каждой версии. Только если без него нельзя решить замечание, поручить его одним заданием всем работающим ревьюерам компашки в ближайшем полном раунде либо отдельной пачкой с той же версией спеки. Не выделять отдельного скаута и не заменять всю работающую компашку одной моделью. Оркестратор перед пачкой фиксирует хеш назначенного дерева разрешённой функцией `snapshot` в `WT_DIR` без изменения его реального индекса и `HEAD`, коммита или ветки. Для всей пачки назначаются одинаковые хеш `SNAPSHOT_TREE`, версия спеки с SHA256 и режим: «база с применением» либо «готовый результат без применения». На этапе 2 назначается базовый снимок до применения проверяемой версии; на этапах 3–4 для проверки выполненного результата – текущий проверяемый снимок без повторного применения уже выполненной спеки. Если проверяется отдельное ещё не выполненное исправление, явно назначаются его базовый снимок и применение именно этого исправления. Назначение снимка, версию и режим записать в журнал, каждое задание и отчёт прогона. Если порученная проверка зависит от diff или индекса, всей пачке дополнительно назначить одинаковое базовое дерево `DIFF_BASE_TREE` и смысл проверяемого изменения относительно него; полный хеш и назначение базы записать там же. Не угадывать базу по `HEAD`; при отсутствии достоверной базы такие команды не выполнять и явно пометить непроверенными. Обычным файловым тестам дополнительная база не нужна. Перед пачкой выполнить условный компакт. В задании каждому ревьюеру обязательно указать:
  - всю последовательность от инициализации до создания temp, клонирования, восстановления, применения при назначенном режиме, проверок и очистки выполнять одним вызовом bash в одной оболочке. Начать с `set -euo pipefail`, затем явно присвоить `WT_DIR` абсолютный путь и `SNAPSHOT_TREE` полный хеш назначенного дерева из текущего задания литералами, без переменных предыдущих вызовов. До использования выполнить `[[ "${WT_DIR:?}" == /* && "${WT_DIR:?}" != / && -d "${WT_DIR:?}" ]]` и `[[ "${SNAPSHOT_TREE:?}" =~ ^([0-9a-f]{40}|[0-9a-f]{64})$ ]]`, затем `readonly WT_DIR SNAPSHOT_TREE`. Создать собственный временный каталог командой `TEMP_DIR="$(mktemp -d)"`, сразу выполнить `readonly TEMP_DIR` и установить `trap 'if [[ -n "${TEMP_DIR:?}" && "${TEMP_DIR:?}" == /* && "${TEMP_DIR:?}" != / && "${TEMP_DIR:?}" != "${WT_DIR:?}" && -d "${TEMP_DIR:?}" && ! -L "${TEMP_DIR:?}" ]]; then rm -rf -- "${TEMP_DIR:?}"; fi' EXIT`. До клонирования выполнить `[[ "${TEMP_DIR:?}" == /* && "${TEMP_DIR:?}" != / && "${TEMP_DIR:?}" != "${WT_DIR:?}" && -d "${TEMP_DIR:?}" && ! -L "${TEMP_DIR:?}" ]]`, затем `git clone --quiet --shared "${WT_DIR:?}" "${TEMP_DIR:?}"`. Не переопределять эти переменные, не отключать строгий режим, guards или обработчик; он удаляет только собственный непустой temp при выходе, в том числе после сбоя;
  - после успешного клонирования, до применения и любых проверок, восстановить назначенное дерево только в собственном клоне в том же вызове bash: выполнить `git -C "${TEMP_DIR:?}" cat-file -e "${SNAPSHOT_TREE:?}^{tree}"`, затем непосредственно перед разрушающей операцией подтвердить собственный temp-клон командами `[[ -d "${TEMP_DIR:?}/.git" && ! -L "${TEMP_DIR:?}/.git" ]]`, `[[ "$(git -C "${TEMP_DIR:?}" rev-parse --show-toplevel)" == "$(cd "${TEMP_DIR:?}" && pwd -P)" ]]` и `[[ "$(git -C "${TEMP_DIR:?}" remote get-url origin)" == "${WT_DIR:?}" ]]`. Только после их успеха последовательно выполнить `git -C "${TEMP_DIR:?}" read-tree --reset -u "${SNAPSHOT_TREE:?}"`, `[[ "$(git -C "${TEMP_DIR:?}" write-tree)" == "${SNAPSHOT_TREE:?}" ]]` и `git -C "${TEMP_DIR:?}" diff-files --quiet`. Во всех последующих командах этого вызова защищать пути `git -C` и назначенное дерево обязательным shell-расширением `${TEMP_DIR:?}`, `${WT_DIR:?}` и `${SNAPSHOT_TREE:?}` соответственно. Переходить к следующей команде и затем к прогону только при успехе каждой предыдущей. Объекты снимка доступны через общее хранилище объектов после `--shared`; исходные `WT_DIR`, его индекс и `HEAD` не менять. При отсутствии объекта, ошибке восстановления или несовпадении не переходить к проверкам и не подменять снимок деревом `HEAD`: записать невозможность прогона и непроверенные команды по общему порядку; очистку только собственного temp выполняет обработчик выхода в той же оболочке. Восстановление переносит вошедшие в снимок изменённые, удалённые и неотслеживаемые неигнорируемые файлы; переноса игнорируемых зависимостей не обещать;
  - в режиме «база с применением» применить только назначенную версию спеки или отдельного исправления по её правилам в своём клоне; в режиме «готовый результат без применения» ничего повторно не применять. Подставлять абсолютный `TEMP_DIR` вместо `WT_DIR` во всех командах, установить зависимости внутри этого клона и запустить только порученные лёгкие проверки, для diff- или индекс-зависимых команд сначала выполнить следующий пункт; длительные тяжёлые прогоны запрещены без явного разрешения пользователя только на указанные команды и объём, прямое указание передавать дословно;
  - для diff- или индекс-зависимых проверок только в режиме «готовый результат без применения» в том же вызове bash явно присвоить `DIFF_BASE_TREE` полный хеш из задания литералом, проверить `[[ "${DIFF_BASE_TREE:?}" =~ ^([0-9a-f]{40}|[0-9a-f]{64})$ ]]`, затем `readonly DIFF_BASE_TREE` и `git -C "${TEMP_DIR:?}" cat-file -e "${DIFF_BASE_TREE:?}^{tree}"`; без успеха этих шагов такие проверки не запускать. Назначить `RESULT_TREE="${SNAPSHOT_TREE:?}"` без нового захвата дерева. Проверить `[[ "${RESULT_TREE:?}" =~ ^([0-9a-f]{40}|[0-9a-f]{64})$ ]]`, затем `readonly RESULT_TREE` и `git -C "${TEMP_DIR:?}" cat-file -e "${RESULT_TREE:?}^{tree}"`; при ошибке зависимые проверки не запускать. Во всех последующих сравнениях защищать параметры через `${DIFF_BASE_TREE:?}` и `${RESULT_TREE:?}`. Для готового результата после восстановления проверять назначенное изменение явным сравнением деревьев, например `git -C "${TEMP_DIR:?}" diff --check "${DIFF_BASE_TREE:?}" "${RESULT_TREE:?}"` и `git -C "${TEMP_DIR:?}" diff --name-only "${DIFF_BASE_TREE:?}" "${RESULT_TREE:?}"`, сохраняя все исходные пути и фильтры порученной проверки. Пустая разница рабочего дерева с уже восстановленным индексом не проверяет результат; `write-tree` и `diff-files` подтверждают только перенос. Адаптация команды допустима только с сохранением её смысла. Скрытые индекс-зависимые команды внутри непереносимого скрипта, неподдерживаемые команды и проверки без достоверной базы не выполнять, записывать непроверенными и передавать исполнителю как обязательные к выполнению и отчёту по общему порядку, не выдавая за успешные. Хеш дерева результата и использованное сравнение записать в отчёте. В режиме «база с применением» новое дерево результата не снимать; diff- или индекс-зависимые команды, точный смысл которых нельзя сохранить по назначенным достоверным деревьям, не выполнять на пустом или неподходящем наборе, а помечать непроверенными и передавать исполнителю как обязательные к выполнению и отчёту по общему порядку. Не подменять результат исходной базой, `HEAD` или предполагаемым хешем. Обычные файловые проверки в этом режиме выполнять по прежним правилам. Реальный индекс и `HEAD` в `WT_DIR` не менять, новых разрешений внешних записей это правило не даёт;
  - пути вне временного каталога и каталога прогона, в которые пишут команды спеки, подменять подкаталогами своего временного каталога; команды, затрагивающие общие клоны, домашние конфиги или не подготовленные оркестратором каталоги, не выполнять и отмечать непроверенными;
  - реальный `WT_DIR` и прочие рабочие копии не менять; дополнительные рабочие каталоги, требуемые инструкциями проекта, например worktree для патчей, готовит и удаляет оркестратор по этим инструкциям и явно передаёт в задании с разрешёнными операциями;
  - команды, результаты и ограничения записать отдельным разделом технического прогона в свой `review-…` или `recheck-…`; для отдельной пачки использовать выданные уникальные пути по правилам каталога прогона, прежние вердикты не затирать. Отдельный тип отчёта для технической проверки не создавать; консультации и существующие экспертные перепроверки сохраняют отдельные артефакты;
  - после прогона, в том числе при сбое, удалить только свой временный каталог; подготовленные дополнительные рабочие каталоги удаляет оркестратор.
- Решение по результатам прогона принимает оркестратор по отчётам ревьюеров. Непроверенные команды и ограничения записывать в журнал и передавать исполнителю как обязательные к выполнению и отчёту, сохраняя запрет тяжёлых прогонов без явного разрешения; не выдавать их за прошедшие. Обнаруженные ошибки спеки исправлять новой версией с ревью по общему порядку. Эти правила необходимого прогона действуют и при разборе замечаний этапов 3–4.
- Записать в журнал путь и SHA256 спеки, подготовить задания всей компашке `ревьюер` с путями к спеке, `task.md`, `facts-<N>.md`, имеющемуся `decisions.md` со всеми полученными ответами и `autonomous-decisions.md`, если он есть. Здесь и во всех планах и проверках этапов 2 и 4 действует общее правило входов: до первого ответа при отсутствии `decisions.md` явно сообщать, что пользовательских ответов пока нет, файл не требовать, фиктивных решений не создавать и отсутствие файла не считать причиной `BLOCKED`. Выполнить условный компакт, затем запустить всю пачку и на точке ожидания вызвать `yield_to_subsessions`. Так же – в каждом повторном раунде.
- При первом ревью требовать от каждого ревьюера до открытия спеки и без чтения кода записать по реально имеющимся `task.md`, фактам, пользовательским и актуальным автономным решениям с общим исключением для отсутствующего до первого ответа `decisions.md` свой план в `plan-reviewer-2-<N>-<модель>.md`: подход, затронутые места, крайние случаи, проверки. Затем открыть спеку, сравнить с планом и расхождения считать кандидатами в замечания.
- Задача роли `ревьюер` – найти места, где буквальный и слабый исполнитель ошибётся: двусмысленности, номера строк и контекст, не совпадающие с реальными файлами, противоречия с `task.md`, имеющимися пользовательскими и допустимыми автономными решениями, пропущенные файлы и крайние случаи, невыполнимые проверки. По фактическим файлам содержательно оценивать наличие, однозначность и применимость каждого фрагмента замены: отсутствующий фрагмент или несколько подходящих совпадений оформлять замечанием, а не выбирать первое совпадение молча. Если конкретное замечание нельзя решить чтением и необходим прогон, действует общий порядок для всей работающей компашки. Эта оценка не обещает равноценности безусловной машинной проверке и не вводит обязательного программного подсчёта или применения каждой версии; допустимые средства обычного ревью не запрещаются. Стиль текста не оценивать.
- При вердикте `REVISE` по каждому замечанию решить: принять и исправить спеку или отклонить с причиной. Решения записать в журнал. Новые развилки решать по правилам этапа 1 и раздела «Автономный режим»; при присутствии пользователя выносить на вопросы, при автономности допустимые решения записывать отдельно.
- При вердикте `BLOCKED`: если хоть что-то из недостающего вне списка передаваемых файлов – сразу остановиться и спросить меня; иначе дополнить задание недостающим и один раз повторить ревью этим ревьюером в том же раунде, а при повторном `BLOCKED` – остановиться и спросить меня.
- Повторное ревью отправлять всей компашке кратко: путь к новой версии спеки, `diff -u` между версиями, прежние замечания и решения по ним. Требовать отметить каждое принятое замечание как `ADDRESSED` или `NOT ADDRESSED`, каждое отклонённое – как `ACCEPTED_REJECTION` или `DISPUTED` с одной строкой контраргумента, и искать новые проблемы только в изменённом.
- По `DISPUTED` самостоятельно не решать и меня не спрашивать, а проводить голосование:
  - два других ревьюера компашки получают замечание, причину отклонения и контраргумент и отвечают одной строкой: `AGREE` – согласен с отклонением, или `DISAGREE`;
  - третий голос – оркестратора;
  - решает большинство из трёх голосов: при отклонении замечание закрыто, иначе спеку исправить. Решение и голоса записать в журнал;
  - если голосов меньше трёх из-за лимитов, при равенстве решает оркестратор.
- Этап пройден, когда все работающие ревьюеры компашки дали `APPROVED` или их оставшиеся замечания закрыты голосованием.
- Одобрение действует только для версии спеки с записанным SHA256. Любая правка после одобрения требует нового ревью.
- При завершении этапа 2 включить автономный режим, даже если порог отсутствия ещё не достигнут, и записать переход в журнал. К этапу 3 переходить, только когда закрыты все развилки и обязательные вопросы, а SHA256 текущей спеки совпадает с одобренным. Перед следующей работой выполнить условный компакт по разделу «Управление контекстом».

## Этап 3. Выполнение и проверка

- Этап выполняется в автономном режиме; обязательные вопросы и приоритет прямых указаний сохраняются. Актуальные автономные решения передавать исполнителю и доработчику вместе со спекой.
- Сделать снимок `T0` в `WT_DIR` и записать его в журнал.
- Подготовить задание роли `исполнитель` с путями к спеке из этапа 2 и к файлу отчёта. Выполнить условный компакт, затем запустить роль и на точке ожидания вызвать `yield_to_subsessions`.
- После завершения сделать снимок в `WT_DIR` и проверить результат:
  - проверки, явно прописанные в спеке, оценивать по отчёту исполнителя с командами, результатами и ограничениями; отсутствующие результаты не считать успешными, самому проверки не запускать;
  - diff от `T0` читать детально на соответствие всему запланированному, а не только тому, что ловит автоматика.
- Самостоятельно не доделывать. При недоделках написать `fix-spec-<N>.md` для роли `доработчик`, чтобы она гарантированно справилась:
  - что не выполнено или сделано неправильно;
  - в каких файлах и строках;
  - как это расходится с согласованными требованиями;
  - что конкретно исправить и как проверить результат.
- Перед каждым запуском доработчика оценить сложность исправлений и записать выбор варианта роли в журнал. Простые – локальные, однозначные изменения с известным способом исправления и проверки, без изменения контрактов и взаимодействия компонентов. Сложные – поиск причины, связанные изменения в нескольких компонентах, асинхронность, состояние, безопасность, совместимость или неоднозначное исправление; при сомнении выбирать сложный вариант. Если простой вариант уже не справился с тем же замечанием, следующий запуск считать сложным.
- Подготовить задание выбранному варианту роли `доработчик`, выполнить условный компакт, запустить роль, на точке ожидания вызвать `yield_to_subsessions`, затем сделать снимок и перед проверкой результата выполнить условный компакт; проверить diff раунда и итог от `T0` целиком. Жёсткая обратная связь допустима, но только вместе с конкретными недочётами, а не вместо них.

## Этап 4. Финальное ревью

- Сначала финальное ревью проводит вся компашка `ревьюер`. Подготовить задания, выполнить условный компакт и запустить всю пачку. Передать пути к файлам:
  - `task.md` – моё исходное задание;
  - `decisions.md` – все полученные ответы, если файл есть; до первого ответа при его отсутствии явно сообщить, что пользовательских ответов пока нет, по общему правилу входов;
  - `autonomous-decisions.md` – актуальные допустимые решения оркестратора, если файл есть;
  - одобренную спеку с решениями по вопросам;
  - спеки исправлений, если были;
  - сводный `facts-<N>.md`;
  - diff от `T0` до текущего снимка.
- При первом финальном ревью требовать от каждого ревьюера до открытия спек и diff выписать по реально имеющимся `task.md`, фактам, пользовательским и автономным решениям с общим исключением для отсутствующего до первого ответа `decisions.md` нумерованный список требований и крайних случаев в `plan-reviewer-4-<N>-<модель>.md`.
- Задача роли `ревьюер` – проверить результат по `task.md`, имеющимся пользовательским и допустимым автономным решениям с общим исключением для отсутствующего до первого ответа `decisions.md` с приоритетом прямых указаний пользователя, а не по спеке: каждое требование свести к строке diff или к замечанию «не реализовано», искать сценарии поломки и изменения вне scope. Соответствие спеке вторично.
- Ошибки финального ревью, скорее всего, сложные и неочевидные: написать по ним `fix-spec-<N>.md` с обязательным тестовым покрытием всех сценариев исправляемой ошибки по разделу «Тесты», подготовить задание роли `исполнитель`, выполнить условный компакт и запустить роль, на точке ожидания вызвать `yield_to_subsessions`. Затем проверить результат по правилам этапа 3, включая цикл доработки.
- Повторное финальное ревью отправлять всей компашке кратко: diff от снимка прошлого ревью, прежние замечания и решения по ним, требование отметить каждое принятое как `ADDRESSED` или `NOT ADDRESSED`, каждое отклонённое – как `ACCEPTED_REJECTION` или `DISPUTED` с одной строкой контраргумента, и искать новые проблемы только в этом diff. По `DISPUTED` проводить голосование по правилам этапа 2.
- При вердикте `BLOCKED` ревьюера или эксперта действовать по правилам этапа 2: недостающее вне списка передаваемых файлов – сразу вопрос мне, иначе один повтор проверки этой моделью в том же раунде, а при повторном `BLOCKED` – вопрос мне. Такой повтор эксперта разрешён.
- Компашка одобрила итог, когда все работающие ревьюеры дали `APPROVED` или их оставшиеся замечания закрыты голосованием.
- После одобрения компашки подготовить задания паре `эксперт`, выполнить условный компакт и запустить пару: она один раз проверяет весь diff от `T0` с теми же файлами и задачей, что у компашки. До открытия спек и diff каждая модель пишет список требований и крайних случаев в `plan-expert-4-<N>-<модель>.md`, а каждое замечание помечает `CRITICAL` или `MINOR`.
- Замечания экспертов разбирать так:
  - принятые исправлять по общему правилу: `fix-spec-<N>.md` → `исполнитель` → проверка по этапу 3;
  - отклонённые оркестратором сразу выносить на голосование, эксперта повторно не вызывать: вся компашка получает замечание и причину отклонения и отвечает одной строкой `AGREE` или `DISAGREE`, четвёртый голос – оркестратора. Голосуют работающие ревьюеры компашки и оркестратор, недоступных по лимитам не ждать. Решает большинство поданных голосов, при равенстве – оркестратор: при отклонении замечание закрыто, иначе исправляется по общему правилу. Решение и голоса записать в журнал;
  - `MINOR` после исправления проверяет компашка по diff исправления;
  - `CRITICAL` после исправления один раз перепроверяет только нашедшая его модель-эксперт: её замечания плюс diff исправления. Ответ сохраняется отдельно в `recheck-4-<N>-<K>-<модель>.md`: по строке на исходное замечание – `ADDRESSED` или `NOT ADDRESSED` со сценарием; новые замечания с тяжестью – отдельно и направлять в общий порядок разбора и исправления этапа 4, без увеличения разрешённого числа вызовов экспертов и без повторного полного экспертного прохода. В ответе инструмента – только итог и путь к этому файлу; исходный вердикт не перезаписывается, новый план не требуется. Если `CRITICAL` нашли обе модели, перепроверяют обе. Если нашедшая модель недоступна, его проверяют компашка и оркестратор в общем лимите раундов;
  - если после перепроверки `CRITICAL` остался `NOT ADDRESSED`, дальше его проверяют компашка и оркестратор в общем лимите раундов. Повторно экспертов для перепроверки не вызывать.
- Этап 4 выполняется в автономном режиме. Вопросы по ревью задавать только в обязательных случаях из раздела «Автономный режим» и по прямому требованию пользователя; допустимые прочие развилки решает оркестратор. Перед итоговым коммитом в той же оболочке определить функцию `snapshot`, получить `MAIN_CHECK="$(cd "${MAIN_DIR}" && snapshot)"` и сравнить с `MAIN0`; при расхождении остановиться и спросить, не исправлять чужие изменения.
- Цикл продолжается, пока довольны все, включая роль `оркестратор`.
- После одобрения итога сделать в `WT_DIR` один коммит всех изменений:
  - проверить `git -C "${WT_DIR}" status --short` и добавить изменения в индекс: если там только файлы из одобренного diff от `T0` – через `git -C "${WT_DIR}" add -A`, иначе только эти файлы поимённо через `git -C "${WT_DIR}" add -- <путь>…`, без установленных зависимостей и посторонних файлов;
  - автор и коммитер – `ORCH_NAME` и `ORCH_EMAIL`, коммит без криптоподписи;
  - сообщение в переменной `MESSAGE` – одна строка в стиле последних коммитов проекта из `git -C "${WT_DIR}" log --format=%s -15`;
  - добавлять `Co-Authored-By` и любые другие трейлеры с упоминанием моделей запрещено.

```bash
GIT_AUTHOR_NAME="${ORCH_NAME}" GIT_AUTHOR_EMAIL="${ORCH_EMAIL}" \
  GIT_COMMITTER_NAME="${ORCH_NAME}" GIT_COMMITTER_EMAIL="${ORCH_EMAIL}" \
  git -C "${WT_DIR}" commit --no-gpg-sign -m "${MESSAGE}"
```
