# Этап 4. Финальное ревью

## Ревью компашки

- Этап выполняется в автономном режиме: вопросы задаются только по обязательным основаниям `references/autonomy.md` и по прямому требованию пользователя, остальные развилки решает оркестратор.
- Снять снимок `WT_DIR` и собрать пакет от `T0` скриптом `review-bundle.sh`. Подготовить задания всей компашке `ревьюер` с входами `references/review-cycle.md`: одобренная спека с материалами первоначальной спеки, спеки исправлений, если были, пакет diff от `T0` до текущего снимка и `references/tests.md` как критерии проверки; при внешних изменениях включить абсолютные пути подготовленных дополнительных каталогов только для чтения по разделу «Дополнительные рабочие каталоги» `references/assignments.md`. Выполнить условный компакт и запустить всю пачку.
- В первом полном раунде каждый ревьюер до открытия спек и diff выписывает нумерованный список требований и крайних случаев в `plan-reviewer-4-<N>-<модель>.md` по `task.md`, ответам пользователя и автономным решениям.
- Задача ревьюера – проверить результат по `task.md`, ответам пользователя и автономным решениям с приоритетом прямых указаний пользователя, а не по спеке: каждое требование свести к строке diff или к замечанию «не реализовано», искать сценарии поломки и изменения вне задачи. Соответствие спеке вторично. Первый полный проход охватывает весь контракт, `autonomous-decisions.md`, каждое принятое свойство в `criteria.md` и каждый пункт `deferred.md` на коде.
- Ошибки финального ревью, скорее всего, сложные и неочевидные: по принятым замечаниям написать `fix-spec-<N>.md` по `references/stage-3.md` с обязательной регрессией по `references/tests.md`, подготовить задание роли `исполнитель`, выполнить условный компакт, запустить роль и на точке ожидания вызвать `yield_to_subsessions`. Затем проверить результат по `references/stage-3.md`, включая цикл доработки; `T0` не меняется.
- Изменение контракта одобренной спеки – по разделу «Изменение контракта» `references/autonomy.md`.
- Перепроверки и повторные раунды – по `references/review-cycle.md`: в пакете повторного ревью – diff от снимка прошлого ревью вместе с полным diff от `T0`.
- Компашка одобрила итог при кворуме `references/review-cycle.md`.

## Эксперты

- После одобрения компашки подготовить задания паре `эксперт` с теми же входами и задачей, что у компашки, включая при внешних изменениях абсолютные пути подготовленных дополнительных каталогов только для чтения по разделу «Дополнительные рабочие каталоги» `references/assignments.md`, выполнить условный компакт и запустить пару. Эксперты один раз проверяют весь diff от `T0`; до открытия спек и diff каждая модель пишет список требований и крайних случаев в `plan-expert-4-<N>-<модель>.md`. Тяжесть замечаний – по единой шкале `references/review-cycle.md`.
- Замечания экспертов разбирать так:
  - принятые исправлять по общему правилу: `fix-spec-<N>.md` → `исполнитель` → проверка по `references/stage-3.md`;
  - отклонённые оркестратором – консультацией всех работающих ревьюеров по `references/review-cycle.md`, без голосования и без повторного вызова экспертов, кроме передачи автору понижения или отклонения `CRIT`;
  - исправление экспертного `WARN` адресно перепроверяет одна работающая модель компашки;
  - исправление экспертного `CRIT` один раз перепроверяет нашедшая его модель-эксперт по своему замечанию и diff исправления в `recheck-4-<N>-<K>-<модель>.md`; если `CRIT` нашли обе, достаточно одной; если нашедшая модель недоступна или после перепроверки осталось `NOT ADDRESSED`, дальше замечание проверяет компашка в общем лимите раундов;
  - исправления `INFO` новых раундов не запускают;
  - новые замечания из перепроверок разбираются в общем порядке этапа 4.
- Повторный полный проход экспертов не запускается.

## Итоговый коммит

- Итог принят при кворуме `references/review-cycle.md` и согласии оркестратора; несогласие оркестратора оформляется замечанием с тяжестью и разбирается в общем порядке этапа 4.
- Перед итоговым коммитом снять `MAIN_CHECK` скриптом `snapshot.sh "${MAIN_DIR}"` и сравнить с `MAIN0`; при расхождении – обязательный вопрос, чужие изменения не исправлять.
- Проверить `git -C "${WT_DIR}" status --short`: если там только файлы из одобренного diff от `T0`, вызвать `commit-project.sh "${WT_DIR}" "${MESSAGE}"`, иначе передать скрипту только эти файлы поимённо, без установленных зависимостей и посторонних файлов. `MESSAGE` – одна строка в стиле последних 15 сообщений коммитов проекта, полученных от скаута вывода `git -C "${WT_DIR}" log --format=%s -15`.
- Добавлять `Co-Authored-By` и любые другие трейлеры с упоминанием моделей запрещено.
- После итогового `commit-project.sh` завершить очистку дополнительных рабочих каталогов, проверку оставшихся следов и запись команд и результатов в журнал по разделу «Дополнительные рабочие каталоги» `references/assignments.md`, затем закоммитить каталог прогона через итоговый `commit-specs.sh`. При окончательной остановке прогона исход очистки, включая обязательный вопрос в блоке остановки при отсутствии подтверждения сохранности результата, определяется тем же разделом; очистка по принятому исходу и её журнал также предшествуют итоговому `commit-specs.sh`. Условия более ранней очистки и повторного создания заданы тем же разделом.
- Слияние ветки, удаление только worktree проекта `WT_DIR` и его ветки выполняет пользователь. В итоговом ответе указать `WT_DIR`, ветку и SHA коммита, затем раздел «Решено без тебя» по `references/autonomy.md`.
