# Этап 2. Спека и её ревью

## Содержание спеки

- Написать `spec-v<N>.md`, с которой справится слабая модель:
  - согласованные требования и решения: ответы пользователя из `decisions.md` и актуальные записи `autonomous-decisions.md`, с приоритетом прямых указаний пользователя;
  - вопросы и ответы пользователя на них;
  - изменения файлов `WT_DIR` только в формах раздела «Форма изменений файлов `WT_DIR`»; другой код в спеку не вставлять, кроме изменений вне `WT_DIR` по правилу о них; команды применения и проверок кодом файлов не считаются;
  - для каждой правки – путь файла, номера строк в текущем коде и точное место;
  - проверки, которые нужно выполнить: только команды и тесты проекта и линтеры, с ожидаемым результатом; допустимые изменения тестов по `references/tests.md`; запрет длительных тяжёлых прогонов без явного разрешения пользователя;
  - условия заданий по `references/assignments.md` для исполнителя.
- Спеку пишет оркестратор. Файлы `WT_DIR`, которые меняет спека, он читает ровно настолько, насколько нужно для «было» и полных замен; остальные нужные факты получает раундом скаутов.

## Защитные правила применения

Единый алгоритм действует для всех пар и блоков первоначальной спеки, внутренних и внешних файлов. На шагах 1–3 режимы сравниваются как восьмеричные значения прав, приведённые к единому четырёхзначному виду: например, `stat -c %04a` для файла и `0755` в спеке; записи `755` и `0755` обозначают одно значение и перед сравнением приводятся к этому виду:

1. Фаза проверки всей спеки: все целевые файлы проходят свои изменения на копиях в собственном временном каталоге роли `mktemp -d` вне целевых каталогов; запись в целевые каталоги запрещена. Для каждого существующего файла сохраняются SHA256 исходного состояния и режим; для нового проверяется отсутствие пути, включая висячую ссылку, иначе `BLOCKED`. Для полной замены существующего файла SHA256 должен совпасть с базой спеки, иначе `BLOCKED`: база файлов `WT_DIR` берётся из `spec-files.sh base` по разделу «Форма изменений файлов `WT_DIR`»; для внешней полной замены оркестратор до одобрения версии вычисляет SHA256 файла в подготовленном каталоге в рамках контроля хешей и записывает в спеку вместе с абсолютным адресом. Техническая проверка сверяет внешнюю базу только чтением. Для каждого нового файла внутри `WT_DIR` и каждой полной замены внутри `WT_DIR` требуемый режим результата должен быть явно указан в спеке по пути или однозначному шаблону путей; режим вложения сверяется с ним, при расхождении или отсутствии указания – `BLOCKED` до публикации любых файлов. Пары на копии применяются последовательно точной заменой в порядке номеров: «было» должно быть точным и уникальным после предыдущих пар, с минимально необходимым контекстом, «стало» – полной заменой. Отсутствующее или неуникальное «было» даёт `BLOCKED` с номером правки; самостоятельный подбор запрещён, в том числе при приоритете инструкций проекта. При любом `BLOCKED` этой фазы ни один целевой файл не изменён; шаги 2–3 запрещены до успешного завершения шага 1 для всех внутренних и внешних файлов.
2. Фаза публикации, подготовка каждого файла: только после успешного шага 1 всей спеки готовое содержимое переносится в новый временный файл с уникальным именем рядом с целью в той же файловой системе; для нового файла нужный каталог создаётся только теперь. Прямая запись в целевой путь запрещена. Режим временного файла задаётся до переименования по форме изменения: для частичной правки парами – сохранённый режим существующей цели, например переносом через `chmod --reference`; для нового файла и полной замены `WT_DIR` – режим вложения, сохранённый `cp -a` во временный файл, без переноса режима цели; для внешних нового файла и полной замены – режим из спеки, а без него у полной замены – сохранённый режим цели, у нового файла – режим по умолчанию инструкций проекта либо `0644`. Режим `0600` от `mktemp` не считается режимом результата сам по себе.
3. Непосредственно перед публикацией каждого файла повторно сверяются SHA256 и режим существующей цели с исходными значениями шага 1 либо отсутствие нового пути, включая висячую ссылку; также сверяется режим подготовленного временного файла с требуемым для этой формы изменения по шагу 2, а для каждого нового файла внутри `WT_DIR` и каждой полной замены внутри `WT_DIR` – с явно указанным в спеке режимом результата. Несовпадение даёт `BLOCKED` без публикации этого файла по шагу 4. Только после успешной сверки временный файл атомарно переименовывается поверх цели одной операцией `mv -f` в пределах одной файловой системы; готовое содержимое не переписывается в целевой путь.
4. При сбое подготовки, записи, сверки или переименования публикация останавливается с `BLOCKED`: текущий файл не публикуется, прежняя цель не перезаписывается, временный файл удаляется. Если ранее опубликованных файлов нет, отчёт фиксирует это и причину сбоя. При частичной публикации отчёт перечисляет опубликованные и неопубликованные файлы и причину остановки, для каждого опубликованного – SHA256 исходного и опубликованного состояния (для нового исходное состояние – `absent`). После работы, включая `BLOCKED` и сбой, собственный временный каталог и все временные файлы рядом с целями удаляются и в результат не включаются.
5. После частичного сбоя публикации исполнителем или доработчиком в реальные целевые каталоги прогона (`WT_DIR` и подготовленные дополнительные каталоги) повтор применения той же или исправленной спеки запрещён до ответа пользователя: обязателен вопрос по `references/autonomy.md` с перечнем опубликованных и неопубликованных файлов и рекомендацией дальнейших действий. Штатный один повтор после `BLOCKED` здесь не применяется; повтор допускается только по полученному ответу с согласованной базой, без повторного применения уже опубликованных правок. Повторное создание дополнительных каталогов определяется только разделом «Дополнительные рабочие каталоги» `references/assignments.md` и не обходит это ограничение.

## Форма изменений файлов `WT_DIR`

- Форма первоначальной спеки этого этапа относится только к файлам `WT_DIR`: вложения `spec-v<N>-files/`, файлы правок `spec-v<N>-edits/`, SHA256-манифесты, база через `spec-files.sh base` и diff полных замен, копирование вложений `cp -a` и запрет других каталогов и файлов к спеке. Эти шаги формы не относятся к внешним изменениям; для всех файлов действуют шаги 1–5 алгоритма раздела «Защитные правила применения». Код файлов `WT_DIR` делить по форме применения, у одного файла – одна форма:
  - новый файл или полная замена – готовое вложение `spec-v<N>-files/<путь>` по пути относительно `WT_DIR`; для каждого такого файла спека явно указывает требуемый режим результата по пути или однозначному шаблону путей, а вложение должно иметь этот режим; исполнитель переносит его без перепечатывания с сохранением прав через `cp -a` по шагам 1–5 алгоритма раздела «Защитные правила применения»;
  - частичные правки – нумерованные пары «было» / «стало».
- Пары подчиняются шагам 1–5 алгоритма раздела «Защитные правила применения» этого файла. Лишний неизменённый код в пары не включать.
- Пары остаются в тексте спеки, только если на файл приходится не больше трёх пар, каждая пара суммарно занимает не больше 10 строк и каждая строка не длиннее 120 символов. Иначе все пары файла выносятся в `spec-v<N>-edits/<путь>.md`.
- Полная замена вместо пар обязательна, если размер правок в байтах не меньше половины размера текущего файла в байтах или если текущий файл не больше 1536 байт и правок минимум две. Размер правок – размер в UTF-8 Markdown-блока всех пар файла в том виде, в каком он стоит в спеке или в файле правок, включая нумерацию, ограждения, «было» и «стало».
- Перед подготовкой полной замены текущий файл читается целиком; восстановление неизменённых частей по памяти запрещено.
- Подготовка версии, если соответствующие каталоги есть; все вызовы `spec-files.sh` с каталогом подчиняются условию наличия из `references/scripts.md`:
  - `spec-files.sh manifest` для `spec-v<N>-files/` и для `spec-v<N>-edits/` – манифесты записываются в спеку;
  - `spec-files.sh base "${WT_DIR}" "${RUN_DIR}/spec-v<N>-files"` – база записывается в спеку: SHA256 текущего файла для полной замены и `absent` для нового;
  - `spec-files.sh replace-diff` только для `spec-v<N>-files/` – `spec-v<N>-replace.diff` для проверки полных замен ревьюерами.
- Пустых каталогов вложений и правок не создавать; манифесты вычислять и перечислять только для существующих каталогов.
- Шаги формы «Применение» ниже – манифесты, `spec-files.sh` и копирование вложений – относятся только к файлам `WT_DIR`; внешние изменения применяются только по разделу «Изменения вне `WT_DIR`». Шаги 1–5 алгоритма раздела «Защитные правила применения» действуют для всех файлов. При отсутствии изменений файлов `WT_DIR` шаги манифестов, базы через `spec-files.sh` и копирования вложений пропускаются. Применение файлов `WT_DIR` в спеке задаётся так:
  - в рамках шага 1 алгоритма раздела «Защитные правила применения» исполнитель сверяет вывод `spec-files.sh manifest` только существующих у версии каталогов вложений и правок с их манифестами; только при наличии `spec-v<N>-files/` сверяет вывод `spec-files.sh base "${WT_DIR}" "${RUN_DIR}/spec-v<N>-files"` с базой спеки. Эти сверки и копирование вложений на временные копии шага 1 выполняются в одном вызове bash с эталоном из текста спеки, без публикации; при любом несовпадении – `BLOCKED` без копирования. Вызовы роли задаются абсолютными путями литералами с обработкой ошибок по `references/assignments.md`;
  - только при наличии `spec-v<N>-files/` вложения обрабатываются по одному файлу из манифеста, каталоги целиком не копировать; применение и режим результата – по шагам 1–5 алгоритма раздела «Защитные правила применения»;
  - при отсутствии `spec-v<N>-files/` сразу переходить к частичным правкам файлов `WT_DIR`, если они есть; применение пар – по шагам 1–5 того же алгоритма.
- Только отсутствие изменений любого вида – вложений и пар файлов `WT_DIR`, внешних блоков кода и внешних пар – ошибка спеки, `BLOCKED`. Спека только с внешними изменениями допустима и выполняется по разделу «Изменения вне `WT_DIR`» без шагов формы и применения файлов `WT_DIR`.
- При спеке для файлов `WT_DIR` не создаются другие каталоги и файлы, в том числе `spec-v<N>-tools/`, и отдельные регрессионные проверки самой спеки.

## Изменения вне `WT_DIR`

- Изменения вне `WT_DIR`, порядок работы с которыми задан инструкциями проекта (`AGENTS.md`, `CLAUDE.md` и подобными), например правки апстрима в worktree патчей `${W}/b`, спека описывает по этим инструкциям прямо в своём тексте с адресом в каталоге из инструкций: новые файлы и полные замены – блоками кода целиком, частичные правки – парами «было» и «стало». Все внешние пары и блоки, включая режимы файлов, подчиняются шагам 1–5 алгоритма раздела «Защитные правила применения» этого файла. Внешние блоки и пары применяются только по указанному адресу в каталоге из инструкций проекта, никогда к `WT_DIR`; к ним не относятся только пороги формы, манифесты, `spec-files.sh` и копирование вложений файлов `WT_DIR`, но шаги 1–5 этого алгоритма действуют без исключения внешних файлов.
- Каталогов вложений и правок для них не заводить и готовых патчей не прикладывать: патчи и прочие производные файлы исполнитель создаёт командами из инструкций проекта.
- Где правила этого этапа расходятся с инструкциями проекта для таких изменений, следовать инструкциям проекта. Запрет дополнительных файлов и каталогов к спеке на такие изменения не распространяется.
- Жизненный цикл дополнительных каталогов, включая подготовку до написания внешних изменений и разрешённое чтение при технической проверке и ревью, – по разделу «Дополнительные рабочие каталоги» `references/assignments.md`.

## Техническая проверка версии

- Выполнимость каждой версии спеки, включая версии только с исправлениями `INFO`, до её ревью или одобрения проверяет скаут – основная модель, при ошибке лимитов вторая – отдельным заданием с отчётом в `spec-check-v<N>-<модель>.md`. Спеки исправлений `fix-spec` технической проверке не подлежат.
- Разрешённые места записи технической проверки – только собственный временный каталог скаута (клон и перенаправленные внешние записи) и свой отчёт в `RUN_DIR`. Разрешения на дополнительные каталоги из других разделов или общих условий заданий здесь не действуют.
- Во входы задания включаются проверяемая спека и её материалы, а при внешних изменениях – абсолютные пути подготовленных дополнительных каталогов только для чтения по разделу «Дополнительные рабочие каталоги» `references/assignments.md`.
- Задание скауту:
  - проверить, что `git -C "${WT_DIR}" status --porcelain` пуст, иначе `BLOCKED`; создать собственный временный каталог `mktemp -d`, клонировать в него `WT_DIR` с Git-историей командой `git clone --quiet "${WT_DIR}" "<temp>/repo"` и сверить `HEAD` клона с `HEAD` `WT_DIR`;
  - выполнить шаг 1 алгоритма раздела «Защитные правила применения» для всей спеки на копиях в собственном временном каталоге; для внутренних файлов подставить путь собственного временного клона вместо `WT_DIR` во всех командах; внешние адреса и базу сверять только чтением подготовленных каталогов по разделу «Дополнительные рабочие каталоги» `references/assignments.md`, внешние изменения воспроизводить только на отдельных копиях, не в клоне `WT_DIR`;
  - после успешного шага 1 всей спеки выполнить шаги 2–3 того же алгоритма только для внутренних изменений в собственный временный клон: он не является целевым каталогом прогона, `WT_DIR` не меняется; при сбое публикации применяется шаг 4 целиком: техническая проверка останавливается с `BLOCKED`, временные файлы удаляются, в её отчёте перечисляются опубликованные и неопубликованные файлы и причина сбоя, для опубликованных – SHA256 исходного и опубликованного состояния по шагу 4, включая `absent` для исходного состояния нового файла; линтеры и проверки неполного дерева не запускаются. Шаг 5 к собственному клону технической проверки не применяется. Первый такой `BLOCKED` допускает штатный один повтор технической проверки той же версии в новом собственном клоне без вопроса пользователю; повторный `BLOCKED` той же версии требует обязательного вопроса по общему правилу `references/autonomy.md` и `references/review-cycle.md`. Техническая проверка новой версии спеки повтором не считается. Это исключение из ограничения записи файлов проекта каталогом `WT_DIR` по `references/assignments.md`; при отсутствии внутренних изменений их шаги пропустить. Линтеры и лёгкие проверки файлов `WT_DIR` запускать на целостном изменённом дереве клона, а не на отдельных копиях или неизменённых файлах; зависимости ставить внутри клона, кэши, `HOME` и временные файлы команд – в подкаталоги собственного временного каталога. Сверить отсутствие лишнего неизменённого кода, а для файлов `WT_DIR` – соблюдение порогов формы и совпадение базы. Внешние изменения остаются только на копиях без публикации в подготовленные каталоги; проверки, которым нужно целостное внешнее дерево, записать непроверенными и передать исполнителю как обязательные к выполнению и отчёту;
  - команды с записью в любые иные места, включая общие клоны, домашние конфиги, подготовленные или неподготовленные оркестратором worktree патчей и прочие внешние каталоги, не выполнять и записывать непроверенными для передачи исполнителю;
  - записать по каждому шагу команду, результат и ограничения, отдельно – список непроверенных команд; после работы, в том числе при сбое, удалить свой временный каталог.
- Симуляция применения файлов `WT_DIR` проводится только во временном клоне, внешних изменений – только на копиях в собственном временном каталоге скаута; симуляция не версионируется и ревьюерам не передаётся. Отчёт технической проверки – внутренний артефакт оркестратора и не предмет ревью.
- По отчёту оркестратор исправляет найденные ошибки спеки новой версией с новой технической проверкой. Непроверенные команды записываются в журнал и передаются исполнителю как обязательные к выполнению и отчёту, не выдаются за прошедшие.

## Ревью

- Записать в журнал путь и SHA256 спеки и манифесты её каталогов, подготовить задания всей компашке `ревьюер` по `references/review-cycle.md` с материалами первоначальной спеки: спека, вложения, файлы правок и diff полных замен, а при внешних изменениях – абсолютные пути подготовленных дополнительных каталогов только для чтения по разделу «Дополнительные рабочие каталоги» `references/assignments.md`. Выполнить условный компакт, затем запустить всю пачку и на точке ожидания вызвать `yield_to_subsessions`. Так же – в каждом полном раунде.
- При первом ревью каждый ревьюер до открытия спеки и без чтения кода пишет свой план в `plan-reviewer-2-<N>-<модель>.md`: подход, затронутые места, крайние случаи, проверки. Затем открывает спеку, сравнивает с планом, а расхождения считает кандидатами в замечания.
- Задача ревьюера – найти места, где буквальный и слабый исполнитель ошибётся: двусмысленности, номера строк и «было», не совпадающие с реальными файлами или неуникальные, нарушения порогов формы и лишний неизменённый код, неверная база, противоречия с `task.md`, ответами пользователя и автономными решениями, пропущенные файлы и крайние случаи, невыполнимые проверки. Стиль текста не оценивать.

## Исправление замечаний

- Решения по замечаниям, тяжесть, свойства и порядок перепроверок – по `references/review-cycle.md`.
- Принятые замечания исправлять новой версией спеки с новой технической проверкой. Исправление `CRIT` и полностью переделанный механизм проверяются полным раундом; исправление `WARN` – адресной перепроверкой автором замечания; исправления `INFO` новых раундов не запускают. Каждое исправление `WARN` и `INFO` без полного раунда записывается в `deferred.md` с проверяемым свойством для проверки на коде этапа 4.
- Новые развилки решать самостоятельно по `references/autonomy.md`: на этапе 2 обычные развилки на вопросы не выносятся, обязательные вопросы сохраняются. Если для развилки, ответа пользователя или нового требования нужны факты, которых нет в `facts-<N>.md`, провести раунд скаутов по `references/stage-1.md`, оставаясь на этапе 2; самостоятельно такие факты не искать.
- Для повторного ревью и перепроверки готовить `spec-v<N>-changes.diff` скриптом `spec-files.sh changes` и передавать его вместе с полным материалом новой версии, а не вместо него.

## Одобрение и завершение

- Одобрение относится к версии спеки с записанным SHA256 спеки и манифестов её каталогов, а не к предыдущей версии; любая правка после одобрения на этом этапе требует новой версии и проверки по правилам тяжести. Изменение контракта одобренной спеки определяется разделом «Изменение контракта» `references/autonomy.md`.
- Версию, отличающуюся от одобренной только исправлениями `INFO`, разрешается отметить одобренной по её актуальному SHA256 без повторного ревью, после успешной технической проверки.
- Этап пройден, когда цикл ревью закончен по кворуму `references/review-cycle.md`. При завершении этапа 2 включить автономный режим, даже если порог отсутствия не достигнут, и записать переход в журнал.
- К этапу 3 переходить, только когда закрыты все развилки и обязательные вопросы, а SHA256 текущей спеки и манифестов совпадает с одобренным. Перед следующей работой выполнить условный компакт.
