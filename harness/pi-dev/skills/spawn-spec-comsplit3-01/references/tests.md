# Тесты

- Прямое указание пользователя создать новые тесты или тестовые случаи выполнять и для существующего, и для нового кода, в том числе если оно дано во время работы. Оно имеет приоритет над ограничениями по умолчанию ниже; учитывать его в актуальных спеке и заданиях, не отказывать из-за того, что случай не относится к особо сложным или ошибкам ревью.
- Прямой запрет пользователя создавать новые тесты выше обязательной регрессии: тогда новых тестов не создавать, а непокрытые сценарии перечислять в отчёте.
- По умолчанию при изменении существующего кода по заданию пользователя актуализировать существующие тесты под согласованное новое поведение, не создавая новые тесты и тестовые случаи, кроме обязательной регрессии ниже.
- При написании нового кода создавать тесты по прямому указанию пользователя, для особо сложных случаев по усмотрению модели либо для обязательной регрессии. По умолчанию в остальных случаях нового кода тесты не создавать.
- Обязательная регрессия «падает до исправления, проходит после» относится только к ошибкам кода продукта, найденным ревьюером или экспертом на этапах 3–4: после исправления покрыть тестами все сценарии проявления ошибки, включая применимые крайние случаи, при необходимости создавая новые тесты и тестовые случаи и для существующего, и для нового кода.
- Для исправлений спеки этапа 2 доказательство «падает до» не требуется и задним числом на этапе 4 не предъявляется. На этапе 2 спека может добавить тест проекта для описанного дефекта без доказательства падения до исправления; отдельные проверки спеки вне проекта запрещены.
- При падении теста сначала тщательно изучить затронутый код, связанные вызовы и причину сбоя: проверить, не внесена ли ошибка и соответствует ли реализация заданию. Ошибку в коде исправлять в коде. Менять тест разрешено только после подтверждения, что его ожидания устарели из-за согласованного изменения поведения; не ослаблять проверки, не удалять и не отключать тест ради успешного прогона.
- Тесты проверяют поведение и результат, а не форму исходников регулярными выражениями, вырезанными фрагментами команд, инструкциями `RUN`, историей образа или heredoc. Исключение – продукт, предметом которого являются линтинг, генерация или формат текста.
- Тесты на тесты и сохраняемые мутационные проверки запрещены без прямого указания пользователя. Однократная временная порча кода для проверки регрессии разрешена с подтверждённым восстановлением и без сохранения проверочного скрипта. Обычные тесты продукта этим запретом не отменяются.
- Ошибки новых тестов текущего прогона исправляются в самих тестах без дополнительного слоя тестирования. Замечания к ним по умолчанию имеют тяжесть `INFO`; `WARN` – пропуск нарушения требований либо ложное падение или зависание в обычном окружении. Тесты продукта – инструмента проверки, изменения существующих тестов и тесты из апстрима остаются обычными тестами продукта.
- Явное разрешение пользователя на длительный тяжёлый прогон передаётся дословно и применяется только к указанным командам и объёму; без него такие прогоны запрещены.
- Эти правила включаются в спеки, спеки исправлений и задания исполнителю и доработчику. Ревьюерам и экспертам они передаются как критерии проверки только на этапе 4.
- В отчёте указывать причины падений, выводы проверки кода, обоснование изменения ожиданий, покрытые сценарии исправленных ошибок ревью, непокрытые сценарии при запрете тестов и команды с результатами. Незапущенные проверки явно отмечать, не выдавая их за успешные.
