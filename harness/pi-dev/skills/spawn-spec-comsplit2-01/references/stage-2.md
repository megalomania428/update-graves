# Этап 2. Спека и её ревью

- Написать `spec-v<N>.md`, с которой справится слабая модель:
  - согласованные требования и решения;
  - вопросы и мои ответы на них;
  - по каждому изменяемому файлу – назначение изменения, форма по правилам ниже и сниппеты либо путь к вложению или файлу правок; другой код в спеку не вставлять, содержимое вложений и файлов правок не пересказывать;
  - проверки, которые нужно выполнить, и допустимые изменения тестов по `references/tests.md`, с учётом запрета длительных тяжёлых прогонов. Проверки исполнителю – только команды и тесты проекта и линтеры.
- Код делить по форме применения, у одного файла – одна форма:
  - новый файл – готовым файлом в `${RUN_DIR}/spec-v<N>-files/<путь относительно WT_DIR>`, без нижней границы по размеру; права задавать на самом вложении через `chmod`, копирование их сохраняет;
  - частичная правка существующего файла – сниппетами в спеке, если у файла не больше трёх пар «было» и «стало», каждая пара вместе не длиннее 10 строк и ни одна строка в них не длиннее 120 символов; иначе все правки файла – файлом правок `${RUN_DIR}/spec-v<N>-edits/<путь относительно WT_DIR>.md`. В обоих случаях – нумерованные пары «было» и «стало» в отдельных блоках кода, перед каждой парой – номера строк текущего файла для ориентира. «Было» – точный текст текущего файла, единственный в нём: изменяемые строки или фрагмент строки и столько контекста, сколько нужно для единственности, обычно 2–3 строки; неизменённый код сверх этого не переносить. Вставка – «было» с соседними строками и «стало» с ними же и новым текстом, удаление – пустое «стало». Ограждение блока длиннее любой серии обратных кавычек внутри него; патчи в формате diff вручную не писать;
  - полная замена существующего файла – только когда размер его файла правок по `wc -c` не меньше половины размера текущего файла по `wc -c` либо текущий файл не больше 1536 байт и правок в спеке или файле правок две или больше. Тогда прочитать текущий файл из `WT_DIR` целиком, положить итоговый файл в `spec-v<N>-files/` по правилам нового файла и удалить его сниппеты из спеки или файл правок; неизменённые части по памяти не восстанавливать;
  - для каждой полной замены дописать diff для ревьюеров командой `diff -u --label "a/<путь>" --label "b/<путь>" "${WT_DIR}/<путь>" "${RUN_DIR}/spec-v<N>-files/<путь>" >>"${RUN_DIR}/spec-v<N>-replace.diff"`, где код возврата 1 означает различия, а не ошибку;
  - в спеке перечислить базу полных замен строками `<SHA256> <путь>` из `cd "${WT_DIR}" && sha256sum <пути>` и пути новых файлов. Исполнитель до копирования выполняет ту же команду `sha256sum`, сверяет значения и убеждается, что путей новых файлов нет; при любом расхождении ничего не копирует и возвращает `BLOCKED`;
  - в спеке перечислить манифесты `scripts/spec-files.sh` для `spec-v<N>-files` и `spec-v<N>-edits` – строки `<SHA256> <путь>`, тогда SHA256 спеки покрывает вложения и правки; пустые каталоги не создавать;
  - дать исполнителю в спеке команду `cp -a "${RUN_DIR}/spec-v<N>-files/." "${WT_DIR}/"` с подставленными абсолютными путями и запретить перепечатывать вложения. Сниппеты и файлы правок исполнитель применяет по порядку инструментом точной замены текста, «было» на «стало»; если «было» не найдено или не единственное, замену самостоятельно не подбирает и возвращает `BLOCKED` с номером правки;
  - каталоги вложений и правок и diff полных замен версионируются вместе со спекой: новая версия спеки – новые каталоги с полным набором файлов и новый diff, прежние не изменять;
  - других каталогов и файлов к спеке не создавать.
- Выполнимость спеки оркестратор сам не проверяет: применение, линтеры и лёгкие проверки поручать основной модели роли `скаут` с отчётом в `check-2-<N>-<модель>.md`, где `<N>` – номер версии спеки. Скаут создаёт временный каталог командой `mktemp -d`, выгружает в него `HEAD` командой `git -C "${WT_DIR}" archive HEAD | tar -x -C <каталог>`, применяет спеку по её правилам, запускает проверки из спеки без длительных тяжёлых прогонов, записывает команды и результаты и удаляет каталог; в `WT_DIR` и прочих рабочих копиях ничего не изменяет. Отчёт – для оркестратора: ревьюерам не передаётся и предметом ревью не является. Оркестратор читает только итог и исправляет спеку по нему до ревью.
- Записать в журнал путь и SHA256 спеки, подготовить задания всей компашке `ревьюер` с путями к спеке, её каталогам вложений и правок, diff полных замен, `task.md`, `decisions.md` и `facts-<N>.md` и провести раунд по `review-cycle.md`.
- При первом ревью требовать от каждого ревьюера до открытия спеки и без чтения кода записать по `task.md`, `decisions.md` и фактам свой план в `plan-reviewer-2-<N>-<модель>.md`: подход, затронутые места, крайние случаи, проверки. Затем открыть спеку, сравнить с планом и расхождения считать кандидатами в замечания.
- Задача роли `ревьюер` – найти места, где буквальный и слабый исполнитель ошибётся: двусмысленности, номера строк и контекст, не совпадающие с реальными файлами, противоречия с `task.md` и `decisions.md`, пропущенные файлы и крайние случаи, невыполнимые проверки, «было», не совпадающее с текущим файлом или не единственное, перенос неизменённого кода в правках, форма файла не по порогу, расхождение манифестов и базы полных замен с файлами. Стиль текста не оценивать.
- Принятые замечания исправлять новой версией спеки. Новый полный раунд ревью запускают только исправление `CRIT` и механизм, переписанный заново. Исправления `WARN` входят в новую версию без полного раунда и проверяются перепроверкой автором по `review-cycle.md`; исправления `INFO` применяются по усмотрению оркестратора без проверки. Номера всех исправлений без полного раунда с проверяемым свойством дописываются в `deferred.md` для финального ревью этапа 4. Новые развилки решать по правилам этапа 1 и `references/autonomy.md`.
- Изменение для повторного ревью и перепроверки автором – путь к новой версии спеки, `diff -u` между версиями, `diff -ruN` между каталогами вложений и между каталогами правок и новый diff полных замен, если они есть.
- Этап пройден, когда цикл компашки пройден по `review-cycle.md`.
- Одобрение действует только для версии спеки с записанным SHA256. Любая правка спеки, вложений или файлов правок после одобрения требует нового ревью, кроме исправлений `WARN` с перепроверкой автором и исправлений `INFO`: SHA256 такой версии записывается в журнал как одобренный вместе с номерами этих исправлений.
- К этапу 3 переходить, только когда закрыты все развилки, а SHA256 текущей спеки совпадает с одобренным. Перед следующей работой выполнить условный компакт по `references/context.md`.
