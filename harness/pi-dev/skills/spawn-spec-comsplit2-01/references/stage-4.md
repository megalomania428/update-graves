# Этап 4. Финальное ревью

<!-- cspell:ignore коммита коммитер ревьюер ревьюера ревьюерами ревьюеры спеке спекой -->
<!-- markdownlint-disable-file MD013 -->

- Сначала финальное ревью проводит вся компашка `ревьюер`: подготовить задания и провести раунд по `review-cycle.md`. Передать пути к файлам:
  - `task.md` – моё исходное задание;
  - `decisions.md` – вопросы и мои ответы;
  - одобренную спеку с решениями по вопросам, её каталоги вложений и правок и diff полных замен;
  - спеки исправлений с теми же их файлами, если были;
  - сводный `facts-<N>.md`;
  - `autonomous-decisions.md` и `criteria.md`, если есть;
  - `deferred.md`, если есть, – исправления спеки без повторного ревью: каждое проверить на коде;
  - diff от `T0` до текущего снимка, собранный `scripts/review-bundle.sh`.
- При первом финальном ревью требовать от каждого ревьюера до открытия спек и diff выписать по `task.md` и `decisions.md` нумерованный список требований и крайних случаев в `plan-reviewer-4-<N>-<модель>.md`.
- Задача роли `ревьюер` – проверить результат по `task.md`, `decisions.md` и `autonomous-decisions.md`, а не по спеке: каждое требование свести к строке diff или к замечанию «не реализовано», искать сценарии поломки и изменения вне scope. Соответствие спеке вторично. Первый полный раунд проверяет весь контракт и каждый пункт `deferred.md`, а не только отдельные места.
- Ошибки финального ревью, скорее всего, сложные и неочевидные: по принятым замечаниям написать `fix-spec-<N>.md` по правилам спеки исправлений из `stage-3.md` с обязательным тестовым покрытием ошибок кода продукта по `references/tests.md` и выполнить её ролью `исполнитель` по `stage-3.md`, включая цикл доработки. Принятые замечания компашки и экспертов исправляются только так; независимые замечания одного раунда – одной спекой исправлений.
- Изменение для повторного ревью и перепроверки автором – diff от снимка прошлого ревью до текущего.
- Проверка исправлений компашки – по тяжести:
  - `CRIT` и механизм, переписанный заново, – полный раунд компашки;
  - `WARN` – перепроверка автором по `review-cycle.md`;
  - `INFO` – оркестратор сам читает diff исправления.
- Когда цикл компашки пройден по `review-cycle.md`, подготовить задания паре `эксперт`, выполнить условный компакт и запустить пару: она один раз проверяет весь diff от `T0` с теми же файлами и задачей, что у компашки. До открытия спек и diff каждая модель пишет список требований и крайних случаев в `plan-expert-4-<N>-<модель>.md`. Формат замечаний и шкала тяжести – из `review-cycle.md`.
- Замечания экспертов разбирать так:
  - принятые исправлять по общему правилу: `fix-spec-<N>.md` → `исполнитель` → проверка по этапу 3;
  - по отклонённым оркестратором сразу проводить консультацию по `review-cycle.md` со всеми работающими ревьюерами компашки, недоступных по лимитам не ждать, эксперта повторно не вызывать: при отклонении замечание закрыто, иначе исправляется по общему правилу;
  - `INFO` после исправления проверяет оркестратор по diff исправления;
  - `WARN` после исправления перепроверяет одна работающая модель компашки по правилам перепроверки автором из `review-cycle.md`, с замечаниями эксперта вместо своих;
  - `CRIT` после исправления один раз перепроверяет только нашедшая его модель-эксперт по правилам перепроверки автором. Если `CRIT` нашли обе модели, перепроверяют обе. Если нашедшая модель недоступна, его проверяет полный раунд компашки;
  - если после перепроверки `CRIT` остался `NOT ADDRESSED`, дальше его проверяет полный раунд компашки. Повторно экспертов для перепроверки не вызывать;
  - механизм, переписанный заново, – полный раунд компашки.
- Поводы спрашивать меня по ревью – только из `references/autonomy.md`.
- Цикл продолжается, пока цикл компашки не пройден по `review-cycle.md`, замечания экспертов не закрыты, а оркестратор не считает итог соответствующим `task.md`, `decisions.md` и `autonomous-decisions.md`.
- После одобрения итога сделать в `WT_DIR` один коммит всех изменений командой `scripts/commit-project.sh "${WT_DIR}" "${MESSAGE}" [<путь>…]`:
  - проверить `git -C "${WT_DIR}" status --short`: если там только файлы из одобренного diff от `T0` – запускать без путей, иначе перечислить только эти файлы поимённо, без установленных зависимостей и посторонних файлов;
  - сообщение в переменной `MESSAGE` – одна строка в стиле последних коммитов проекта из `git -C "${WT_DIR}" log --format=%s -15`;
  - автор, коммитер и запрет трейлеров – по `references/scripts.md`.
- Слияние ветки и удаление worktree выполняю я. В итоговом ответе мне указать `WT_DIR`, ветку, SHA коммита и раздел «Решено без тебя» по `references/autonomy.md`.
