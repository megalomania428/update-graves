# Тесты

Действует на этапах 2–4.

- Прямое указание пользователя создать новые тесты или тестовые случаи выполнять и для существующего, и для нового кода, в том числе если оно дано во время работы. Оно имеет приоритет над ограничениями по умолчанию ниже; учитывать его в актуальных спеке и заданиях, не отказывать из-за того, что случай не относится к особо сложным или ошибкам ревью.
- По умолчанию при изменении существующего кода по заданию пользователя актуализировать существующие тесты под согласованное новое поведение, не создавать новые тесты и тестовые случаи, кроме обязательного покрытия исправленной ошибки ревью по правилу ниже.
- При падении теста сначала тщательно изучить затронутый код, связанные вызовы и причину сбоя: проверить, не внесена ли ошибка и соответствует ли реализация заданию. Ошибку в коде исправлять в коде. Менять тест разрешено только после подтверждения, что его ожидания устарели из-за согласованного изменения поведения; не ослаблять проверки, не удалять и не отключать тест ради успешного прогона.
- При написании нового кода создавать тесты по прямому указанию пользователя, для особо сложных случаев по усмотрению модели либо для обязательного покрытия исправленной ошибки ревью. По умолчанию в остальных случаях нового кода тесты не создавать.
- Тесты проверяют наблюдаемое поведение и результат, а не текст исходников: не вырезать фрагменты кода из файлов для отдельного запуска и не проверять регулярками форму записи команд, инструкций сборки, истории образа или тел heredoc вместо их результата. Исключение – задачи, где предмет работы – сам линтер, генератор или формат текста.
- Обязательная регрессия действует для ошибок в коде, то есть на этапах 3 и 4, включая спеки исправлений: после исправления ошибки, найденной ревьюером или экспертом, обязательно покрыть тестами все сценарии проявления этой ошибки, включая применимые крайние случаи. Это исключение действует и для существующего, и для нового кода: при необходимости создавать новые тесты и тестовые случаи; проверки должны воспроизводить ошибку до исправления и проходить после него.
- На этапе 2 кода ещё нет, и замечание исправляется новой версией спеки. Если оно описывает дефект поведения, который тесты проекта не поймают, спека добавляет или меняет тест проекта вложением или правкой в `WT_DIR`, а ревьюер по тексту оценивает, покрывает ли тест сценарий. Доказательство «падает до исправления» для таких тестов не требуется, на этапе 3 они должны проходить. Отдельные проверки спеки вне проекта ради регрессии не создавать.
- Эти правила включать в спеки и задания исполнителю и доработчику; ревьюерам и экспертам передавать их как критерии проверки только на этапе 4. В отчёте указывать причины падений, выводы проверки кода, обоснование изменения ожиданий и покрытые сценарии исправленных ошибок ревью. Ограничение на длительные тяжёлые прогоны сохраняется; незапущенные проверки явно отмечать, не выдавая их за успешные.
