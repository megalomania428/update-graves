# Duplicacy with patches

<!-- markdownlint-disable MD013 -->
<!-- cspell:ignore duplicacy gilbertchen goproxy GONOSUMDB GOPRIVATE GONOPROXY dpx Keychain xattr setfattr Setxattr pipefail GOARM riscv ppc goroutines errorf -->

Patched build of the [Duplicacy](https://github.com/gilbertchen/duplicacy) CLI, distributed in [GitHub Releases](https://github.com/megalomania428/update-graves/releases) as binaries and as a file-based GOPROXY with the Go module `duplicacy.invalid/v3`. Upstream has no tag for 3.3.0, so `build.yaml` pins commit `c8530c4d0fd4b607fd3e0fd98db359f6d7a15a19` with `version: 3.3.0`, `patch: 2` and `patch_width: 3`: the release version is `3.3.0-p002` and the Go module version is `v3.3.0-p002`. Pull requests and manual builds use `3.3.0-p002.dev.<run>.<attempt>` and the shared `v999` draft. Every build runs all upstream Go tests and integration tests before packaging, and one target publishes nothing if any of them fails.

A release has these assets, where `<version>` is the file-name form `3_3_0-p002`:

- `duplicacy-<version>-<os>-<arch>.txz` for `linux-amd64`, `linux-arm64`, `linux-386`, `linux-arm` (ARMv7, `GOARM=7`), `linux-riscv64`, `linux-ppc64le`, `darwin-amd64`, `darwin-arm64`, `freebsd-amd64` and `freebsd-arm64` – one binary named like the archive without the extension; the Linux and FreeBSD binaries are fully static, and the build fails if `file` does not report them as statically linked;
- `duplicacy-<version>-windows-amd64.7z` and `duplicacy-<version>-windows-386.7z` – the same binary for Windows with `.exe`;
- `duplicacy-<version>-goproxy.txz` – the `duplicacy-<version>-goproxy` directory of the file-based GOPROXY.

Installation on Linux x64:

```bash
curl -fsSL 'https://github.com/megalomania428/update-graves/releases/download/duplicacy-v3.3.0p002/duplicacy-3_3_0-p002-linux-amd64.txz' | tar -xJ -C /tmp
install -m 0755 /tmp/duplicacy-3_3_0-p002-linux-amd64 ~/.local/bin/duplicacy
```

`duplicacy -h` shows `VERSION: 3.3.0 (c8530c4 3.3.0-p002)`: the upstream version, the short upstream commit and the recipe version. All binaries are built with `CGO_ENABLED=0`, so the macOS binaries cannot use the Keychain: enter passwords interactively or pass them through `DUPLICACY_PASSWORD` and the other `DUPLICACY_*` environment variables.

## Go module

The module path is `duplicacy.invalid/v3`, and the package is imported as `duplicacy "duplicacy.invalid/v3/src"`. The `.invalid` domain is reserved by RFC 6761 and never resolves, so without the file proxy `go` fails at once instead of fetching an unrelated repository. The module requires Go 1.26.0 or newer.

```bash
gh release download duplicacy-v3.3.0p002 -R megalomania428/update-graves \
  -p 'duplicacy-*-goproxy.txz' -D /tmp/dpx
tar -C /tmp/dpx -xf /tmp/dpx/duplicacy-*-goproxy.txz
export GOPROXY="file://$(echo /tmp/dpx/duplicacy-*-goproxy),https://proxy.golang.org,direct"
export GONOSUMDB='duplicacy.invalid'
go get duplicacy.invalid/v3@v3.3.0-p002
```

Never set `GOPRIVATE` or `GONOPROXY` for `duplicacy.invalid`: they disable every proxy for the module, `file://` included. `GONOSUMDB` only skips the public checksum database, which cannot know this module.

## List of patches

- `001-linux-xattr-strict-tests` – `-exclude-by-attribute` works on Linux: the `user.duplicacy_exclude` attribute (`setfattr -n user.duplicacy_exclude <file>`) is matched with its namespace, as `github.com/pkg/xattr` returns it. `TestEntryExcludeByAttribute` sets the Linux attribute through `github.com/pkg/xattr`, the library of the production code, and fails on its errors: `github.com/gilbertchen/xattr` reports every successful `setxattr` on Linux as `errno 0`. Integration tests run under `set -euo pipefail` and accept `TEST_ZONE` from the environment; `resume_test.sh` no longer fails on the missing `file3`, requires its three deliberately failing backups to fail and uses files of up to 199 bytes, so a run with fewer than eleven chunks is practically impossible. `duplicacy_main.go` logs script output through a constant `%s` format, so the vet checks of `go test` pass with Go 1.26. `TestChunkOperator` sets the global logging level to `INFO` instead of `DEBUG`, which leaked TRACE and DEBUG output into every later test and flooded CI logs; a comment there explains switching back to `DEBUG` to investigate its failures and the alternative of a deferred reset to `INFO`.
- `002-worker-errors` – a panic of a worker task or of a background goroutine of `Backup`, `Restore`, `CheckSnapshots`, `Diff`, `PruneSnapshots`, `ListSnapshots`, `ShowHistory`, `CopySnapshots` or `Benchmark` no longer exits the process from its goroutine: it is recorded and raised again by the operation in the goroutine that called it, unless the operation has already returned or panicked by itself, so the CLI exits with the same code while a program embedding the library can recover it. This covers chunk uploads of `Backup`, which skip the queued uploads once an upload failure has been recorded and keep the first recorded failure, while later ones are not raised; chunk downloads of these operations, including the snapshot sequences downloaded through the operator of the snapshot manager, which skip the queued downloads once a task has failed and, unless failures are allowed, raise a failed download; the local and remote listing goroutines of `Backup` and `Restore`, the local listing of `Diff` and the verifying goroutines of `CheckSnapshots`; and the delete, fossilize and resurrect tasks of `PruneSnapshots`, which raise their errors also when the prune returns without waiting for them, so that no fossil collection is saved after such a failure, while a chunk that can't be deleted remains a warning. It also covers the chunk downloads and uploads of `CopySnapshots`, which keep the first failed chunk of either, raise it and stop adding and running chunks once a chunk of either has failed, and the uploading and downloading goroutines of `Benchmark`, which raise a failed chunk instead of reporting success. After such a failure no goroutine of the operation is left behind; these operations keep an operator that the snapshot manager had before them, but not its failures, nor the fossils collected by a prune, so `CheckSnapshots`, `Diff`, `PruneSnapshots`, `ListSnapshots` and `ShowHistory` no longer stop and remove it, while these five operations, `Backup`, `Restore` and `PrintFile` replace an operator stopped by an earlier operation, or clear the failures that an earlier operation has left on it, when they start, instead of blocking or reporting a failure of another operation, and `Restore` also no longer leaves a worker blocked by a chunk prefetched for a skipped file. `CopySnapshots` likewise keeps an operator that the source snapshot manager had before it, but not its failures, replaces a stopped one or clears the failures left on it when it starts, and stops the operator it has created to download the snapshot sequences, and its count of copied chunks, which the uploading goroutines increase, is updated atomically. With allowed failures a failed download remains a warning: `Restore` counts the failed files and `CheckSnapshots` reports the corrupted chunks as an error, and the worker no longer returns the broken chunk to the chunk pool after passing it to the receiver, which returns it too, so two workers can't get the same chunk. The local listing closes its channel also when it can't read the top directory, so that `Backup`, `Restore` and `Diff` don't block on it. An entry of the level `ERROR` or above is raised as an `Exception` also after a `LogFunction` that returns, as it is without one, so that an operation of a program that sets `LogFunction` stops at the error instead of going on with a wrong state, such as a backup that overwrites the latest revision because it can't be read. `SuppressLog` and the `-suppress` option hide only the entries up to `WARN`: an entry of the level `ERROR` or above is not hidden by them and stops the operation as well, so that the CLI no longer goes on after a suppressed error, such as a `check` that reports success although chunks are corrupted. The patch also fixes the five `go vet` findings of upstream: `net.JoinHostPort` for the SAMBA address, the timeout context of the Swift storage released when the storage can't be created, the `json` tags of `DataShards` and `ParityShards` written with double quotes and keeping their keys, and the discarded `fmt.Errorf` result in `CheckSnapshot`, whose entry check errors are still not returned, as in upstream.
- `003-progress-callback` – the package variable `ProgressFunction func(ProgressEvent)`, unless nil, receives structured progress events of `Backup`, `CopySnapshots`, `Restore`, `CheckSnapshots` with `checkChunks` or `checkFiles` and `PruneSnapshots`, so that a consumer of the module doesn't parse log messages: a start with the known totals; a step for each file chunk of `Backup`, uploaded or skipped, each chunk that `CopySnapshots` copies, each file chunk that `Restore` or `CheckSnapshots` with `checkFiles` downloads and each chunk that `CheckSnapshots` with `checkChunks` verifies, with its length, the bytes written to the storage (always 0 for `Restore`, `CheckSnapshots` and `PruneSnapshots`, even if `CheckSnapshots` with `rewriteChunks` rewrites a corrupted chunk), whether it was skipped, whether it is a metadata chunk and its id, and a step for each delete, fossilize or resurrect task of `PruneSnapshots` that succeeds or finds its result already there, with its action, whether it found its result already there, whether its chunk is a metadata chunk and its id – a task that fails, such as a delete task that fails to remove its file or a fossilize or resurrect task that fails to move it, has no step, while a fossilize or resurrect task that finds its result already there reports it even if it fails to remove the chunk file left over; and an end with the number and length of the new file and metadata chunks of `Backup` or the copied chunks, the bytes written to the storage, the number of chunks that `Restore` has downloaded or `CheckSnapshots` with `checkChunks` has to verify, and the failures: the skipped files and directories that `BACKUP_SKIPPED` of `Backup` reports, the files that `Restore` failed to restore, as many as it returns, the corrupted chunks that `SNAPSHOT_VERIFY` of `CheckSnapshots` with `checkChunks` reports, the files of all revisions that `CheckSnapshots` with `checkFiles` failed to verify and the delete tasks of `PruneSnapshots` that failed to remove the files of their chunks, each logged as a `CHUNK_DELETE` warning; a dry run of `Backup` reports the bytes that it would write. The operation, the kind of an event and the action of a step are string types with exported constants, and the numbers are `int64`. The hook is called regardless of `showStatistics`, `RunInBackground` and the logging level, possibly concurrently from the worker goroutines and the goroutine that runs the operation; a start without an end means that the operation failed or was canceled, but an end doesn't mean a success: `Restore` and `CheckSnapshots` with `checkChunks` report their failures in the end, after which a check with corrupted chunks fails, and `PruneSnapshots` with no revision to delete reports its end and returns `false`; a panic of the hook is raised by the operation like any other panic of it. The counters of the new metadata chunks in `UploadSnapshot`, which the worker goroutines updated without synchronization, are updated under a lock, so that the end and `BACKUP_STATS` count every metadata chunk. Log messages are unchanged.
- `004-cancel` – `RequestCancel()` asks the running `Backup`, `CopySnapshots`, `Restore`, `CheckSnapshots` or `PruneSnapshots` of a program that embeds the module to stop; it may be called from any goroutine, `ProgressFunction` included, and doesn't block. The operation stops adding new tasks at its next check, lets the tasks already queued finish and panics in the goroutine that called it with an `Exception` whose `LogID` is `CancelLogID` (`OPERATION_CANCELED`), logged through `LOG_ERROR`, so that `LogFunction` receives it; a failure that a worker has already recorded is raised instead. A cancellation requested before the operation starts is raised before anything is changed, while one requested after its last check doesn't stop it. The request stays set until `ResetCancel()`: an operation doesn't clear it, so the consumer calls `ResetCancel()` before the next operation, and `IsCancelRequested()` reports it. `Backup` checks the request while it compares the local and the remote files, before each file and each chunk that it packs and, after the queued chunks have been uploaded, before it uploads the snapshot; no revision is created. A hash backup – the first one or one with `-hash` – that is canceled after it has started packing tries to save its incomplete snapshot, unless it is a dry run, and the next hash backup of the repository resumes it; if the saving fails, it only logs an `INCOMPLETE_SAVE` warning and that backup packs the files again, skipping the chunks that are already in the storage; a cancellation during the comparison saves nothing. `CopySnapshots` checks it before adding each chunk and before writing the revisions, so a canceled copy writes no revision and the next copy copies only the missing chunks. `Restore` checks it while it compares the local and the remote files, before each file and before it deletes the extra files and restores the metadata of the directories, so the files restored before stay, and so do the directories and the symbolic links that the comparison has already created, while the extra files aren't deleted and the metadata of the directories isn't restored. A restore through a temporary file also checks it before it writes each chunk downloaded from the storage, while the chunks already prefetched are still downloaded, and leaves the target as it was, removing the temporary file; chunks copied from the existing file aren't checked. An in-place restore, whether explicit or forced by `Restore` even with `inPlace` false when `GetDuplicacyPreferencePath()` doesn't start with `top`, writes into the target and stops only between files, so a large file is completed first. `CheckSnapshots` checks it before it downloads each revision file, before it checks each revision and, with `checkChunks`, before it queues each chunk; the chunks already queued are verified, and only the intact ones are saved to the list of verified chunks, so the next check skips only them. With `checkFiles` a revision is verified as a whole, so the check stops only between revisions. `PruneSnapshots` checks it before it lists the revisions of each snapshot ID and before it downloads each revision file, between the old fossil collections, where it first waits for the tasks of the previous ones, before it chooses the revisions to delete and for each snapshot ID while choosing them, before it reads the chunks of each revision and, in the non-exhaustive mode, once more before it fossilizes or deletes the first chunk; in the exhaustive mode it checks it before it lists each chunk directory and after the listing until it adds the first fossilize, delete or resurrect task, which a dry run never adds. A prune canceled after it has created its log writes `Prune canceled` there, unless a failure of its tasks is raised instead. A canceled prune changes the storage at most through the old fossil collections it has already processed, none with `collectOnly`, and not at all in a dry run: the fossils and temporary files of such a collection that is eligible for deletion, which is a collection that has passed the deletion criteria or, in the exclusive mode, any collection, may be deleted or the fossils turned back into chunks, while a collection that isn't eligible is left as it is. In the local directory of the collections in the snapshot cache, not in the storage, a canceled prune has removed at most the file of a processed collection that is eligible, except in a dry run, and the file of a collection that lists a revision that still exists, in a dry run too and without touching the fossils of that collection; with `collectOnly` it touches no file of the collections. The tasks of an old collection are a step that ends before the check ahead of the next collection, so a request made while they run cancels the prune if another collection or a later check follows. The chunks, the new fossil collection and the deletion of the revision files are one step that isn't stopped, since stopping it would leave fossils without a collection or, in the exclusive mode, revisions whose chunks are deleted. It starts after the last check before the first fossilize or delete task of the revisions to delete in the non-exhaustive mode and with the first fossilize, delete or resurrect task of the chunk scan in the exhaustive mode: a request made then lets the prune complete and return `true`, and so does one made with `deleteOnly` after the check of the last old collection. A canceled operation reports no end through `ProgressFunction`, and one canceled before its start reports no events at all. Other operations and the CLI don't use the request.
