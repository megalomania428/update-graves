# `@raven428/pi-subagents`

<!-- markdownlint-disable MD013 -->
<!-- cspell:ignore nicobailon sessiond subagent subagents worktrees herdr -->

Patched build of [pi-subagents](https://github.com/nicobailon/pi-subagents), distributed as the `@raven428/pi-subagents` npm tarball in [GitHub Releases](https://github.com/megalomania428/update-graves/releases). The upstream ref and the patch number live in `build.yaml`: `ref: v0.69.0` with `patch: 1` sets the package version to `0.69.0-p1`. Pull requests and manual builds use `0.69.0-p1.dev.<run>.<attempt>` and the shared `v999` draft. The tarball holds the compiled `dist-pkg` tree that upstream publishes.

Installation into the agent profile of the PI WEB session daemon, for example:

```bash
npm i -g 'https://github.com/megalomania428/update-graves/releases/download/pi-subagents-v0.69.0p1/pi-subagents-0_69_0-p1.tgz'
npm root -g
```

Then add the absolute path `<npm root -g>/@raven428/pi-subagents` to `packages` in `settings.json` of the agent profile the daemon uses (`PI_CODING_AGENT_DIR`), remove an upstream `pi-subagents` package from that profile, and restart the session daemon so its sessions load the extension. The package requires Pi 0.85.1.

## List of patches

- `001-pi-web-hosted-children` – run custom agents as sessions of the unmodified `@raven428/pi-web` 1.202609.0-p8 daemon that hosts the parent session, instead of in-process children; outside a PI WEB daemon nothing changes
  - Detection: the parent is hosted when `PI_WEB_SESSION=1` and `<PI_WEB_DATA_DIR or ~/.pi-web>/sessiond-owner.json` names this process (pid and `/proc` start time); processes merely spawned from a PI WEB session keep the upstream behavior. A process started from pi-web's `dist/server/sessiond.js` whose marker is missing, unreadable or names another process gets an error before launch instead of in-process children. The daemon is reached over its own socket or fixed TCP port, and `/health` must report pi-web `1.202609.0-p8` (or one of its draft builds) and Pi `0.85.1`; anything else is an error before launch.
  - Launch: the `subagent` tool, foreground `workflowScript` (`runs.run`/`runs.all`) and `/run <agent> <task>` write a fresh child session file next to the parent's file, with the parent's cwd, `parentSession` pointing at the parent file, a `piSubagentsChild:true` header marker, the child's name and a `pi-subagents.web-child-policy` entry holding the agent contract; then they open it through the daemon, wait until the child confirms the contract, and prompt it through `POST /sessions/:id/prompt`. Several children run in parallel as separate PI WEB sessions. Deviation from upstream: a launch without `async` (including every step of a workflow and `/run`) runs in the foreground here, because PI WEB hosts only foreground children. As for foreground runs upstream, a second `subagent` call or `/run` of the same parent while a foreground run is in progress is refused ("a subagent call is already in progress"); several children run at once through `runs.all`. Agents with an external runner (`runner.type` `external-cli` or `external-job`) run only in the background upstream and are refused here regardless of `async`. `forceTopLevelAsync:true` is also refused here, including when `async` is omitted or `false`; the error names that setting rather than suggesting an overridden parameter. The daemon owns execution and lifecycle: finishing a run only stops observing the child, its runtime stays as PI WEB keeps it.
  - Contract on every open: pi-subagents, loaded in every session of the daemon profile, restores the agent model and thinking level, the child hooks of upstream (prompt runtime, tool budget, permissions, structured output, watchdog), the exact tool set with a `tool_call` guard (a tool the agent lists but the profile lacks locks the child), and the agent system prompt, rendered with a pinned copy of Pi 0.85.1 `buildSystemPrompt` from the options Pi itself used. The copy must reproduce Pi's base prompt first, otherwise the child is locked. Upstream prompt semantics are kept: `replace` replaces SYSTEM.md, `append` replaces the discovered APPEND_SYSTEM.md. Deviation from upstream: PI WEB's environment fact sections (`<pi_web_session_environment>`, `<pi_web_docker_environment>`) stay after the agent prompt. While the launching run observes the child its live hooks are used; an open without that run (after the run, a daemon restart or a reopen from the browser) rebuilds the hooks from the policy, records structured output and watchdog status in the child's state file, treats the other parent observers as absent and locks the child if the launch carried any other value that data cannot hold. The tool budget counts over every open: the state file keeps the calls counted so far, a later open gets the remaining limits as upstream gives a resumed run, and a child whose hard limit is used up is locked. A reopen while the launching run still observes the child and after part of the budget is used locks the child as well. A run whose agent prompt an extension loaded after pi-subagents replaced in its own `before_agent_start` is aborted before its tools run; appending to the prompt is allowed.
  - Fail-closed applies only to a session identified as a child by a detectable ledger, a policy entry or the pi-subagents header marker: such a child whose policy is missing, altered or written for another Pi, whose state file is missing, unreadable, incomplete or cannot be updated, whose model is unavailable or unauthenticated, or that was stopped, answers every input with an explanation, blocks every tool and aborts any run; a run that starts without the agent prompt (for example an extension's triggered message) is aborted and its tools are blocked. When two prompts reach an idle child at the same moment, Pi drops the agent prompt of the run that won; that run is aborted before its next model request and both prompts fail with an explanation. Slash commands typed into a locked child still run, because Pi gives extensions no way to veto another extension's command; any model turn they trigger is aborted. Pi `/fork` and `/clone` of an opened child copy its policy entry but have no ledger for the new session id, so those copies are locked, not ordinary usable sessions. A child opened from the browser in a profile without pi-subagents is not protected – install the package in the daemon profile.
  - Not hosted (error before anything is created): explicit async/background runs and workflows (`async:true`, `/run --bg`), `context:'fork'`, resume, chains, `tasks`, worktrees, a cwd other than the parent's, nested launches from a hosted child, pane-native placement, agent `extensions` (including the extension path pi-subagents adds for permission rules with pi-permission-system), per-child environment. Agent model references must name an exact `provider/id[:thinking]` of the daemon profile.
  - Control: the browser and the orchestrator address the same session. `subagent({ action: "steer" | "interrupt" })` reach the running child through PI WEB; addressed tool steer accepts run ids, session ids and unique session id prefixes, including while the launch is still preparing its child, and reports success only after companion acceptance. PI WEB decides at delivery whether to queue into a running turn or start a new turn, so a turn ending during the send is not a steering error; `subagent({ action: "steer", id, message })` addressed to an idle, not stopped child of this parent (session id, unique id prefix or run id) is the explicit continuation: a new turn in the child's own session whose answer the tool returns, where upstream steering recovery would resume the run (resume stays refused; `steeringRecovery: false` keeps the plain upstream refusal); `subagent({ action: "stop", id })` on a foreground run is a terminal stop of its children. A terminal stop locks a child that is still open at once, records the tombstone and closes the runtime; when the tombstone cannot be recorded the runtime is still closed and the stop reports the error, and stopping again records it. A steer or follow-up of the orchestrator waits for the companion to accept its token-bearing input; a child locked between the initial check and input delivery fails with the lock reason instead of reporting delivery. Aborting the orchestrator's turn (Stop in its chat) aborts the turn of its running foreground child, which stays usable. The orchestrator's model can also call `subagent({ action: "interrupt" })` in the same message as the foreground launch, because Pi runs the tool calls of one message in parallel: the run is interrupted the same way once its child step has started, and before that the call fails with `No interrupt-capable run found in this session.` and interrupts nothing. Closing or reloading the parent aborts all its children recovered from this parent's ledgers or bounded, marked child headers, including detached children and children continued after an earlier parent runtime; their sessions remain. Failed enumeration or abort is reported by a parent notification and diagnostics rather than silently skipped. Each prompt of the orchestrator is registered before it is posted and claimed by the child on the matching input, so only the turn that carries it settles the run: a turn started from the browser just before it is not taken for the orchestrator's, and a run reports `aborted` or `failed` as the child saw it. The sender appends a unique request token to the transport text. On `input`, the companion accepts a registered transport envelope (surrounding prefix/suffix transformations are supported), replaces its own token with a fresh input capability and removes all other quoted tokens. Only that accepted capability can carry the request identity through `before_agent_start` into the per-turn system-prompt marker used at `agent_start`; merely quoting a completed, pending or cancelled request token grants no ownership and never applies that request's cancellation to the browser turn. Quoted transport comments are removed from persisted new input; accepted capabilities remain visible there, and all such comments are stripped from user messages in the model context. Another accepted request may quote someone else's token without stealing that request. Ambient extensions after the companion must preserve its input capability when transforming input. Pi expands `/template-name` prompt templates after `input`, including continuation and steer text: a template that does not carry its argument tail (including the capability comment) drops correlation, so the turn runs without the request identity and the caller keeps waiting for a definite outcome. Such templates are unsupported for correlated requests; plain text or templates preserving the complete argument tail retain correlation. Before the companion, transformations must preserve the registered envelope, not just a quoted token: Pi exposes no immutable authenticated per-prompt identity that could distinguish an arbitrary rewrite from a browser quoting that token (or a browser replaying the entire envelope). Profiles that remove the envelope before acceptance or the capability afterward cannot guarantee correlation or cancellation of that rewritten input without also blocking unrelated browser input. An input accepted while Pi is running is not yet evidence of delivery to that turn: only a user message carrying its fresh capability binds it to the executing turn. The companion observes PI WEB queue snapshots from Pi's queue updates and requests `GET /sessions/:id/status` on every event-stream connection, including reconnects. An input seen queued and then discarded without delivery receives its own `aborted` outcome when that run ends, including Stop in the child's browser chat. After an observation gap, a claim still present in the queue remains observed, and a delivered claim retains its own turn's outcome through the in-process companion channel. An undelivered claim absent from the queue at an idle snapshot receives `aborted` and remains durably cancelled if the companion observed Pi's current-run `ExtensionContext.signal` abort after accepting that claim, including a browser Stop during the observation gap. Abort observation lasts until Pi reaches idle at `agent_settled`, not merely the companion's `agent_end`: Stop during another extension's delayed `agent_end` still marks delivered and discarded queued claims as `aborted`. Pi is already idle and has released that run's abort signal before calling `agent_settled` handlers, so a later Stop there cannot retroactively cancel that completed run. The same signal makes delivered claims `aborted` even when interruption happens inside a tool, including `structured_output` or another tool returning `terminate: true`, without any assistant message ending as aborted. Natural tool termination without abort stays completed. Without that interruption evidence it fails explicitly with `Delivery unconfirmed: queue observation was interrupted.` and remains durably cancelled, rather than guessing that it completed or was aborted. Without an observation gap, input still delayed in another extension's input chain is not mistaken for discarded queued input. Pi exposes no per-input completion witness to the companion, and pi-web returns from POST before that input chain finishes: following an observation gap, a still-delayed input can therefore receive `aborted` with that interruption evidence or the explicit unconfirmed-delivery failure without it at idle; its eventual delivery is absorbed before the model and tools instead of hanging the caller. A delayed follow-up retains its capability across the earlier turn's settlement and receives its own turn's outcome; a cancelled delayed input is discarded with a notification before it reaches the model or tools.
  - `/subagents-web` in the parent chat, answered as text without a model turn: `doctor`, `status [child]`, `steer <child> <message>`, `follow-up <child> <message>` (queued into a running turn, or a new turn of an idle child), `abort <child>` (the child stays usable), `stop <child>` (terminal: tombstone, abort, close, and every later input is refused), `result <child>` (last saved assistant answer and structured output), `reconnect <child>` (reopen and re-check the contract). A child is addressed by session id, a unique id prefix or run id. Slash results of `/run` are shown in the PI WEB chat, and `/subagents`, `/subagents-fleet` and `/subagents-stop` answer with their text output there instead of terminal selectors. Explicit `/subagents <agent> model|thinking|prompt` edits are unavailable in this text-mode admin workflow and report the reason and a terminal Pi/configuration-file alternative instead of silently showing metadata.
  - Request failures: PI WEB `session.error` has neither a request id nor an operation source; shell, slash and other prompts publish the same event. It never rejects an accepted request. Event-stream disconnects reconnect without rejecting a delivered turn; the companion's in-process claim and outcome channel remains authoritative, and reconnect snapshots reconcile undelivered claims as described above. Slow `input` and `before_agent_start` handlers are not treated as failure. Slash and adapter steer/follow-up wait for acceptance or a definite refusal/shutdown without a claim timer; HTTP acceptance alone is not success. A failed POST or lost HTTP response does not reject input already claimed by the companion: steer/follow-up still report acceptance, and launches and continuations keep observing their actual outcome. A send is refused only when cancellation is confirmed; a claim that wins cancellation remains authoritative. A refused send retains durable cancellation of any delayed registered input instead of withdrawing its identity. If Pi drops a prompt before a turn (including input handled by another extension or missing model or credentials), or input never reaches the companion, no correlated failure is available: the caller waits for a companion outcome, runtime shutdown, explicit cancellation or the configured agent timeout. Without a configured timeout or cancellation these cases can wait indefinitely; continuations accept the orchestrator's cancellation signal. Timeout, cancellation and observation disposal release observation claims but retain a cancelled input's unique token until its own turn is aborted before the model, its input is consumed, or the runtime closes; no time window expires the cancellation. A delayed unclaimed cancelled input is consumed with a visible child-chat notification, while identical browser text stays usable. Pre-turn cancellation is acknowledged by the companion without an unscoped daemon abort; a running turn is cancelled through the daemon, and an HTTP abort failure is reported as an error rather than an aborted outcome. Tool steer and continuation share the correlated sender's cancellation result: neither an outer wait nor a concurrently received acceptance/outcome can report cancellation before the inner durable cancellation finishes or hide its error. Its claim remains until the real turn outcome, and the ledger stays running while the turn is running. A timeout hard finish before daemon acknowledgment explicitly reports that cancellation is unconfirmed and the child may still be running; an abort failure received later is retained as the ledger's last error and shown by status. `/subagents-web abort` snapshots all current accepted and registered-but-unaccepted request ids before posting and durably cancels only those requests after the daemon confirms cancellation; late input is consumed with a notification and an aborted outcome. Requests registered after the snapshot and unrelated browser input are not cancelled; a failed POST leaves the turn's actual outcome intact. Cancellation never attaches to a different turn merely because that turn starts while the HTTP response is pending. Recreating a child refuses an existing unreadable or damaged ledger instead of replacing its stop history. Stop uses a healthy ledger without needing to read the parent directory; damaged-ledger recovery reads only bounded session headers and cannot recover addresses from an unreadable directory. Without a policy, a child is identified only by an existing ledger. A `parentSession` header and the filename are not child markers: ordinary Pi fork/clone sessions use them too and remain usable, including when the ledger directory is inaccessible. New children carry the package's own `piSubagentsChild:true` header marker, which also permits parent cleanup when ledger enumeration fails; ordinary Pi fork/clone headers do not carry it. Legacy headers without this marker cannot establish child identity when their ledger is inaccessible; cleanup reports that uncertainty visibly. When a run id cannot be resolved because ledgers are corrupt or unreadable and no companion knows the run, stop reports the cause and requests the child's session id or unique prefix instead of falling back to async-run diagnostics. If policy, marker and detectable ledger are all absent, the session cannot be distinguished from an ordinary session and is not protected; a readable policy, marker or detectable ledger still locks a damaged child.
  - State: the run state of each child (prepared, running, settled, aborted, failed, stopped, with the stop tombstone, the outcome of the last correlated turn, the tool calls counted against the budget and output recorded without the launching run) lives in `<agent dir>/pi-subagents/web-children/<child id>.json`, separate from the session itself.
  - Tests: unit tests for the prompt split, policy and runtime serialization, session file, ledger and daemon detection; a contract test of the adapter against a scripted daemon; an opt-in test of the companion on the real Pi 0.85.1 SDK (`PI_SUBAGENTS_NATIVE_PI_ROOT`, see `test/integration/web-companion-native.test.ts`) and an opt-in end-to-end test through the web process of an isolated installed pi-web (`PI_SUBAGENTS_PI_WEB_ROOT`, see `test/integration/web-pi-web-e2e.test.ts`: tool launch without `async`, parallel workflow children, an abort from the chat of the orchestrator's running child with the result reaching the orchestrator, the orchestrator's continuation of that idle child, an abort of the orchestrator's turn interrupting its running child, command listing, `doctor`, `/run`, steer, follow-up, abort, browser reconnect to a running child, reopen, status and terminal stop), both with a deterministic provider.

## Nesting without refresh

The unmodified pi-web announces a new session only when it creates it itself, so a prepared child appears under its parent after the session list is reloaded (choosing the workspace again or refreshing the page). The patch already contains the client side of a host API; pi-web gets live nesting by implementing it:

- announce `pi-subagents.child-session.parent.v1` in `capabilities` of `GET /runtime`;
- accept `POST /sessions` with `{ cwd, sessionId, sessionFile, parentSession, name, entries }`, where `sessionFile` is in the session directory of `cwd` and `entries` are `custom` entries to write after the `session_info` entry; create the session file exactly there with `parentSession` in its header, answer `{ id: sessionId, path: sessionFile }` and publish the usual `session.created` event, so connected browsers insert the child under its parent at once.

With the capability present the adapter lets PI WEB create the child and does not write the file itself; without it the adapter keeps the prepared-file path. Further improvements on the PI WEB side: an event or flag for "turn settled" on the session WebSocket, a request id for `POST prompt` to correlate prompts and turns, and an extension gate that refuses to open a session whose required extension is not loaded.
